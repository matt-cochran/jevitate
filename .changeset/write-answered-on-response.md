`journey verify --mutate` now treats a `no-store` write as answered once its body has been reported. A POST answered with `Cache-Control: no-store` whose body the page does not read never reports that it finished, so a proof read `inconclusive` ("a write still unanswered") about a request answered in milliseconds; those proofs can now reach a verdict, at up to 2s per replay with such a write. A write a new document sends keeps its reported body when that document's DOMContentLoaded comes. Any other response keeps its write open until it finishes, and a response alone answers nothing: a server that sends its headers and keeps working still reads `inconclusive`. A write answered and then aborted, or dropped with its document, gets 2s too. Stated in `docs/outcomes.md`: a `no-store` body whose first bytes have arrived, on a page that reads it, holds an unread clone or used `sendBeacon`, reads as answered after those 2s, which can be a false reading; an unread `no-store` body over about 2 MB, or a write from a dedicated worker or a popup as it opens, stays `inconclusive`. A block-write now also notices its write being answered after the block when the body is unread. `journey run`: a `responseStatus` check on such a request now reads its status instead of failing with "still awaiting a response"; a gRPC-web or Connect response still waits for its body, since its result can be in the trailer.
