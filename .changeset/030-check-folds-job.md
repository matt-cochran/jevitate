**Breaking change for CI users: `jevitate check` now folds each Journey item's job.** Every Journey item of a check suite (and of MCP `run_check`) reads its job's done check, as `journey run` does, and folds the verdict with the project's `doneCheckPolicy`. A job not achieved (the steps passed, the done check still read false) fails the item on a gating `done-check-failed` finding, so the check exits 1. A Journey item that passes with an unverified job (no done check, `--no-done-check`, or one already true) now makes the check exit 2 under the default `require`, where it exited 0; a pass on a `trust: "harness"` environment still exits 0 and reads `unverified`/`harness`. The verdict is carried in `check.json` (`items[].job`, `doneCheckPolicy`, `summary.unverified`), each item's `result.json`, JUnit (case properties `jevitate.job.attainment` and `jevitate.job.basis`, and `<failure type="done-check-failed">`), SARIF (the finding, plus `doneCheckPolicy` and `jobs` run properties) and `report.md` ("Job verdicts"). New flags `--no-done-check` and `--require-done-check` (MCP `doneCheck: false`, `requireDoneCheck`), refused together (exit 64). `campaign run` and MCP `run_campaign` fold each discovery replay's job the same way (`discovery[].jobVerdict`): not achieved exits 1, unverified turns a clean campaign into exit 2 under `require`, and it never hides a defect a mission found; they take the same two flags, forwarded to the discovery replays only. **Migration:** add a `done` check to each job your suites' Journeys link (`.jevitate/jobs.json` `jobs[].done`), or keep the old exits with `"doneCheckPolicy": "advisory"` in `.jevitate/project.json`.
