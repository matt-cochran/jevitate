**Behaviour change over MCP.** A value for a secret Journey parameter (declared `secret: true`, or named like a credential) is now refused with `E_SECRET_PARAM_OVER_MCP` before anything runs, on `run_journey`, `verify_journey`, `journey_readiness`, `chain_journeys`, `demo_journey`, `annotate_journey`, `run_load_test`, `run_exploration` and `sources`. These calls used to run with the value, which meant it had passed through the model. `${setup.x}` references are unchanged, and so are params that are not secret, with one exception: a name that reads as a credential, described below. `run_journey` with `env` or `baseUrl` now reads the value from the `secretFields` for that origin in `targets.json`, so a request can leave it out. A secret in a `navigate` URL has no field to bind, so it now runs on the CLI only.

`journey run` takes `--secret-field '<label|testId|id|name>=<value>=env:<VAR>'`, the binding a Journey is authored with, and `targets.json` `secretFields` apply to it with `--env` or `--base-url`, so a secret parameter stays off the command line. `--param` with a secret parameter keeps working on the CLI and now warns on stderr. See `docs/journeys.md`.

Which names count as credentials changed, everywhere that name check is used. It is now deliberately broad, and adds `pwd`, `authorization`, `auth`, `bearer`, `jwt`, `pin_code`, `privateKey`, `accessKey`, `key`, `mfa`, `ssn`, `cvv`, `csrf`, `signature`, `nonce`, `card_number`, `webhook_url` and foreign words for password, so these are redacted and refused over MCP. A stored Journey under such a name still loads: assertion references and request-body shapes keep their older, narrower rule. `passengers`, `token_count` and other ordinary names that match stay refused over MCP until the parameter declares `"secret": false` and a person approves that Journey (a typed `journey promote` or a verified PR review). An approval over MCP, a scripted or unrecorded one, or a stale one lifts nothing, and a source's Journey can't lift it.

A value `--secret-field` or `targets.json` supplies is only typed on its own origin (the entry's, or for the flag the run's allowlist), checked on `fill`, `select` and `editText` with the field in hand: anywhere else, as after a redirect, the step fails with `E_SECRET_ORIGIN_REFUSED`. Two secret parameters on one binding, or two bindings on one parameter, now refuse before anything runs instead of typing a guessed value. A fixture output named like a credential is redacted and left out of `fixtures.outputs`, in `secretOutputs` or not. A self-heal's model payload and evidence screenshots now redact fixture secrets and extracted credentials too. `verify-fix` and `regression` `--param` warn for a secret parameter.

With `HOME` overridden and the working directory below the account's real home, the real `~/.jevitate` no longer reads as a project, so logs stay under `HOME`. It still counts when it holds an `environments.json`, when the home is the working directory's git root, or, outside any repo, when it holds no per-user files. The review sheet warns about `secret: false` on a credential-like name.
