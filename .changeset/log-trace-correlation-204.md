Backend-log correlation by trace or correlation id (#204), and `--log-scope` (#282). Every request the run's page sends is recorded with its correlation ids (`traceparent`, `x-request-id`, `x-correlation-id`, `request-id`, `x-amzn-trace-id`, `x-b3-traceid`, `x-cloud-trace-context`, plus `--log-correlation-header <name>`). A `--log-source` line that carries one of them is attached to that exact request (`request: { method, url, status, id }`) and to the step that sent it, whenever the line landed; lines with no id still use the time window. Once ids correlate, a line with another request's id (another user, a background job; recognized as `trace_id=`/`request_id=`/`correlation_id=`, a `traceparent`, or `--log-id-pattern </regex/>`) is never attributed to the run. A `blocked`/`exhausted`/`inconclusive` goal reason now composes the UI blocker with its correlated server cause: `…; caused by: error "…" on POST /api/publish (409)`. `--log-scope <regex|substring>` attributes only matching lines (e.g. a tenant id) when concurrent runs tail one log; the rest count as `serverLogs.ignoredLines`, and `verify-fix` keeps the scope. `serverLogs.correlation` reports `requestsWithIds`, `idMatchedLines`, `foreignLines` and `outOfScopeLines`. The three flags are also suite options and `targets.json` keys (`logScope`, `logCorrelationHeaders`, `logIdPatterns`). They are omitted from MCP like every log-source option. A usability run now also honours `--log-quiet-ok` and `--log-ignore`.
