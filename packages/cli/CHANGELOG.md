# @jevitate/cli

## 0.30.0

### Minor Changes

- 81312e7: **Exit code change.** A goal run that covers every control it can reach, with none leading toward the goal, now ends `inconclusive` (exit 2) with `goalReason: "no-route-found"` and `failure.kind: "no-route-found"`. It ended `blocked` or `exhausted`, exit 1. Its reason lists the pages it opened. Code decides the coverage floor: every top-level navigation page opened, no untried control left on a page it saw, no control naming the goal, and nothing clickable the run cannot use (an `onclick` element outside a control, a canvas, a frame). Below the floor the run ends as before. A role word on the page ("Viewer", "Read-only", "Guest") is named as a hint that another role may see more, never as a wall (#807).
  
  **Exit code change.** A goal run that passes while its job's final done-check reading is false (`--job`, `job.attainment: "not-achieved"`) now exits 1 `defects-found` with `failure.kind: "done-check-failed"`. It exited 0. This holds under either `doneCheckPolicy` and whatever verified the pass: the find-out exemption covers only a job that nothing verified.
- 81312e7: `jevitate journey shorten <id> --job <jobId> [--budget n] [--out-id <id>]` (#801): an authoring-time search for a shorter path to the same job, with no model. It removes steps (delta debugging), replays every candidate in full with the Journey's fixtures (or `--fixtures`) set up before and restored after it, and decides each one only by the job's done check, read in a fresh browser context. It never drops a click on a confirm, agree or accept control, and never keeps a navigate past one it dropped; those candidates cost no replay. The budget (default 30 replays) includes the recorded path's own replay. The output is a new, unpromoted draft Journey (`<id>-shortest`) and a report of the original steps, the shortest found and the replays used; the source Journey is not changed, and a person reviews and promotes the draft. The result is the shortest path found within the budget, not a proven optimum, and it is only as honest as the done check: a weak check lets a path that skips real work through. Over MCP it is the new `shorten_journey` tool (the same report): draft Journeys only (a promoted one is refused `E_JOURNEY_SHORTEN_PROMOTED`), under `run_journey`'s run-mode gate and run guard (an unapproved draft runs on a test-mode target only), and a secret parameter is refused by name (`E_SECRET_PARAM_OVER_MCP`).
- 81312e7: A secret in a `navigate` URL, such as an invite token, now has a route off the command line (#819). `--secret-field 'param=<name>=env:<VAR>'` binds a secret parameter by its name, wherever the Journey uses it, and the same spec works in `~/.jevitate/targets.json` `secretFields`. A bound value goes only to its binding's origin: the replay checks the URL as resolved before it navigates, and a URL whose literal origin is another one is refused with `E_SECRET_ORIGIN_REFUSED` before anything runs. Over MCP, on an automation-mode target, `run_journey` sends it from the operator's `targets.json` binding for that origin. With no binding, the run is refused with `E_SECRET_MODE_UNAVAILABLE` before any browser opens, and the message names the binding, because a person can't type a URL at a hold. The `--param` warning now names the `param=<name>` binding, which works for a URL secret. A goal run never matches a `param=` binding to a field.
- 81312e7: Every command that replays a Journey now takes a secret parameter off the command line, and no secret value sits in a file at rest (#827). `journey verify`, `journey demo`, `journey chain` (the `--from` Journey), `load run`, `source run`, `regression capture`/`run`, `verify-fix`, `journey migrate --labels` and `campaign run` take `--secret-field`, as `journey run` does. All of them except `source run` also read the environment's `targets.json` `secretFields` with `--env` or `--base-url`. `explore --from-journey` gives its prefix replay the `--secret-field` bindings that match the prefix, and so does a sweep (`--at-step all|anchors`) at every stop.
  
  A secret value in a `check` suite's `params` or a campaign spec's `params` is refused by name (`E_CHECK_SUITE`, `E_CAMPAIGN_SPEC`), whether the name looks like a credential or the Journey declares it secret. The suite target's `secretFields` (`'param=<name>=env:VAR'`, which holds only the variable's name) and the operator's `targets.json` supply it instead.
  
  Over MCP the value comes from the operator's `targets.json` binding for the run's origin, never from the call's arguments or a file the call named. `verify_journey`, `demo_journey`, `chain_journeys` and `run_check` handle a secret the call leaves out the same way `run_journey` does. `run_load_test` and `run_exploration` (`fromJourney`) use the binding only, and without one are refused with `E_SECRET_MODE_UNAVAILABLE`: a load test or a mission's prefix never holds. `jevitate inbox resume` of a hold a `journey chain` producer reached resumes the producer and then runs the consumer for each matched request, so the whole chain runs. `sources` over MCP still never reads `targets.json` for a source's Journey.
  
  Fixed: an adversarial mission's `scope.routeGlobs` held a prefix's URL secret in plain text, in stdout and in the result file. The `--param` warning names each command's own `--secret-field`.
- 81312e7: Publish repository-catalog contract v3.0.0 under `contracts/jevitate-catalog/v3/`. It adds the job done check (`jobs[].done`) and typed Journey parameters (`type`, `enum`); because the closed v2 schemas refuse files that use them, v3 is a new contract major. The v1.0.0 and v2.0.0 contracts ship unchanged beside it. Catalog bundles now pin the v3 manifest in `catalogContract`.
- 81312e7: **Breaking changes.** (1) A run that passes but has no job done check now exits 2 (`inconclusive`) where it exited 0. The default `doneCheckPolicy` is `require`, and it applies to `journey run`, `run_journey`, queued Journey calls, and goal runs started without `--success` or `--job`. Set `"doneCheckPolicy": "advisory"` in `.jevitate/project.json` to keep exit 0. (2) A boundary run (a wall, a lost session, a write off the allowlist, or a link that opens a new tab) now exits 2 `inconclusive` with `goalOutcome: "boundary"`; it exited 1 `defects-found`. A CI script that read 1 as "the job is broken" should expect 2 here. (3) A Journey whose steps pass but whose done check reads false now exits 1 `defects-found` (`failure.kind: "done-check-failed"`); it exited 0. (4) `journey verify --mutate` reports `verdict: "sensitive"` where it reported `"proven"`, with `verdictLegacy: "proven"` beside it until 0.32.0. A script that tests `verdict === "proven"` should read `verdictLegacy` now. (5) Mutation proof is advisory: the job's done check is the gate, and `mutationProofPolicy` stays `advisory` by default (`require-sensitive` replaces `require-proven` as the opt-in for targets you can reset). (6) `jevitate check` suites (and MCP `run_check`, `campaign run`/`run_campaign` discovery) fold each Journey item's job: a job not achieved is a gating `done-check-failed` finding (exit 1), and a Journey item that passes with an unverified job makes the suite exit 2 under `require`, where it exited 0. Add done checks, or set `"doneCheckPolicy": "advisory"`, to keep a CI gate green. What to do: add a `done` check to each job in `.jevitate/jobs.json` (or set the advisory policy), re-read exit 2 in your CI as "could not tell", and update any script that tests `"proven"`.
  
  - Job done checks and attainment (#800). A job in `.jevitate/jobs.json` takes an optional `done` field: a statement about the app's state, read by code in a fresh browser context before step 1 and after the end state. `journey run`, `run_journey`, goal runs and queued calls report `job: { attainment: "achieved" | "not-achieved" | "unverified", basis }`. `explore --goal --job <id>` and `run_exploration {job}` use the job's check as the success check, and a queued exploration carries its job. `--no-done-check` and `--require-done-check` set the policy for one run. `journey lint` warns `missing-done-check` and `done-check-cannot-be-false`, and `journey link` and `journey find` show the check. A goal run on a target you declare `trust: "harness"` still exits 0 on a pass and reads `unverified` (#802).
  - Adjudicator (#812). `journey verify` gathers evidence and a small, pure verdict function decides; Jev does not. Every `journey run` and `journey verify` writes a value-free `evidence.json` (`RunEvidence` v1) in its logs folder. The 0.29.0 `journey-run-*.json` record is unchanged and deprecated.
  - Run modes and trust (#792). A run is in test or automation mode, decided only by `trust` in `.jevitate/environments.json` and `~/.jevitate/targets.json` (`test`, `harness`, `production`; the stricter wins; an undeclared target is automation). A Journey promoted over MCP authorises test-mode runs only; automation runs need an approval typed at a terminal or a reviewed PR (`E_APPROVAL_CHANNEL_FOR_MODE`). To run an MCP-promoted Journey against anything else, run `jevitate journey promote <id>` at a terminal, or declare a real test target `trust: "test"`. A test-mode run never waits for a person (`E_HUMAN_STEP_IN_TEST_MODE`), and a proof never holds (`E_HUMAN_STEP_IN_PROOF`, exit 2). `check --require-trust` fails a run on an undeclared target.
  - Holds and secrets (#793, #798). In automation mode a Journey with a secret step holds there instead of refusing: the value comes from `targets.json` `secretFields` (it goes to the browser, never the model) or from a person. A held run ends `outcome: "held"`; `jevitate inbox approve <id>` (at a terminal) and `jevitate inbox resume <id>` continue it from a checkpoint bound to the Journey, parameters, target and pending step (`E_HOLD_BINDING`, `E_HOLD_EXPIRED`). A secret value as an MCP parameter is still refused (`E_SECRET_PARAM_OVER_MCP`).
  - Limits an agent cannot loosen (#799). Over MCP, `site_policy` can only tighten (`E_POLICY_LOOSEN_OVER_MCP`) and `mission_targets` cannot promote a target (`E_TARGET_PROMOTE_OVER_MCP`). `queue_journey` is added to the served tools, under the same promotion and mode rules as `run_journey` (#797); it is the only tool added. `jevitate journey queue` is its CLI twin, `mission result` looks up a queued call, and an orphaned call is recovered.
  - Reconcile and receipts (#795). A run's result carries per-write receipts, and a retry or resume reads the job's done check first, so a write that already landed is not repeated.
  - Typed Journey parameters (#796) are refused before any browser with `E_JOURNEY_PARAM_TYPE`, naming the parameter and type, never the value. `journey find` shows parameter types, and repository-catalog contract v3 describes them.
  - Write sentinel (#794). With `JEVITATE_WRITE_SENTINEL=shadow` and a Jev key, Jev records which writes it would have held, from structure only (control role and name, method, path shape, job). It holds nothing in 0.30.0.
  - Secrets off the command line and out of files (#819, #827). Every replay command takes a secret parameter from the environment: `--secret-field '<field>=<value>=env:VAR'`, or `'param=<name>=env:VAR'` for any secret parameter, a token in a navigate URL included. With `--env` or `--base-url` the origin's `targets.json` `secretFields` work the same way. Over MCP the value comes only from the operator's `targets.json` or a hold, never from the call's arguments. A secret value written in a `check` suite or a campaign spec is now refused by name. Bind it in the target's `secretFields`, which hold only the variable's name. `inbox resume` of a hold a `journey chain` producer reached runs the whole chain. See the #819 and #827 notes.
  - Goal runs (#807, #810). A "Sign in with..." goal may type and submit, and a credential typed from the goal text is never stored or sent on. Return-to-start no longer goes back to a sign-in page. A link that opens a new tab is read from the DOM, and a standing hang names the app's last request. Goal runs return to an earlier page with untried controls before a dead-end stop.
  - Fixes. `editText` reports `E_EDIT_NOT_APPLIED` when nothing was typed; a short secret inside a longer token is masked on goal, adversarial and usability runs; an `extract as` name counts as a credential only on a real credential word; log pruning counts a run's evidence folder with its record (#790); a persistent profile whose TMPDIR is too long for Chromium's socket is refused with a clear message; the Journey proof rules pair requests causally and a declared block/skip contradiction is refused (#811, #813, #821).
  
  Limits: an agent that can write `.jevitate/` or `~/.jevitate/` can still forge `trust` and an approval's channel; review those files in git. A done check is only as good as its author. A proof's strength depends on a target you can reset, and a proof on any other target reports `countsForGate: false`.
- 81312e7: `journey readiness` gates on the job, and the mutation proof is advisory there too (owner decision "Proof role"). The receipt leads with a `job` check: the latest run's `job.attainment` passes when `achieved`, blocks (exit 1) when `not-achieved`, and when `unverified` (no run of this version, no done check, a run from before 0.30.0) follows `doneCheckPolicy`: `require` (the default) exits 2 with the reason and the fix, `advisory` shows it without gating. Under the default `mutationProofPolicy: advisory`, a missing, stale or insensitive proof no longer blocks readiness (it was exit 2 or 1) or fails `journey review --strict` (it was a ⚠); it is the checks-strength line, marked `advisory: true` on the receipt. An unwaived `inconclusive` proof does not gate under `advisory` either (it was exit 2); `require-attempt` / `require-sensitive` gate as before. Every `journey run`, `run_journey` and queued call now records `job: {attainment, basis}` (code tokens only) and `journey.proofHash` in its `journey-run-*.json`; `journey review` shows the latest run's job verdict first (`job` in `--json`). What to do: run each Journey once with a done check before `journey readiness`, or set `"doneCheckPolicy": "advisory"`.

### Patch Changes

- 81312e7: **Breaking change for CI users: `jevitate check` now folds each Journey item's job.** Every Journey item of a check suite (and of MCP `run_check`) reads its job's done check, as `journey run` does, and folds the verdict with the project's `doneCheckPolicy`. A job not achieved (the steps passed, the done check still read false) fails the item on a gating `done-check-failed` finding, so the check exits 1. A Journey item that passes with an unverified job (no done check, `--no-done-check`, or one already true) now makes the check exit 2 under the default `require`, where it exited 0; a pass on a `trust: "harness"` environment still exits 0 and reads `unverified`/`harness`. The verdict is carried in `check.json` (`items[].job`, `doneCheckPolicy`, `summary.unverified`), each item's `result.json`, JUnit (case properties `jevitate.job.attainment` and `jevitate.job.basis`, and `<failure type="done-check-failed">`), SARIF (the finding, plus `doneCheckPolicy` and `jobs` run properties) and `report.md` ("Job verdicts"). New flags `--no-done-check` and `--require-done-check` (MCP `doneCheck: false`, `requireDoneCheck`), refused together (exit 64). `campaign run` and MCP `run_campaign` fold each discovery replay's job the same way (`discovery[].jobVerdict`): not achieved exits 1, unverified turns a clean campaign into exit 2 under `require`, and it never hides a defect a mission found; they take the same two flags, forwarded to the discovery replays only. **Migration:** add a `done` check to each job your suites' Journeys link (`.jevitate/jobs.json` `jobs[].done`), or keep the old exits with `"doneCheckPolicy": "advisory"` in `.jevitate/project.json`.
- 81312e7: Done checks, made to match the 0.30.0 decisions. A goal run on a target declared `trust: "harness"` (`explore --job`, `run_exploration`, a queued exploration) now reads `job: { attainment: "unverified", basis: "harness" }` and exits 0 on a pass, as `journey run` does; it could read `achieved` (#802). A find-out goal whose grounded answer was accepted keeps exit 0 under `doneCheckPolicy: "require"`, since it claims no end state; `--require-done-check` still makes it exit 2. `explore --job` with a job id the catalog does not have (`E_EXPLORE_JOB`) now exits 64, a usage error, where it exited 2. A Journey that links no job may carry its own done check in `metadata.done`, in the jobs.json shape: `journey run` reads it, `journey lint` checks it by the same rules (and refuses it beside a linked job, whose check always wins), and the review sheet shows it.
- 81312e7: Every surface that replays a Journey and reports its pass now reads the job's done check and folds it into the exit, as `journey run` and `run_journey` do: `journey chain` / `chain_journeys` (the producer and each consumer; `job` on `from` and on each run), `inbox resume` (the resumed run, or the whole chain), and `source run`. A job not achieved exits 1 (`failure.kind: "done-check-failed"`); an unverified pass exits 2 under the default `doneCheckPolicy: "require"`. Before, these surfaces exited 0 on a pass whatever the job. A self-heal run's `*.result.json` now keeps `job` and the folded exit code. A hold made by a chain's producer also binds the consumer Journey's content hash and the requests file's sha256; `inbox resume` refuses (`E_HOLD_BINDING`, `consumer` or `requests`) when either changed since.
- 81312e7: Over MCP, a site policy that adds or lowers a pause or reading ceiling (`max`, `maxReadingMs`) is now refused as looser, even where the effective policy set none. The queue drain also recovers a mission or Journey call left `queued` by a drain that died right after claiming it, and no longer mistakes a reused PID for the claimant (claims record the process start time and a per-drain nonce). The root export no longer includes the test fake `fakeDoneJudge`.
- 81312e7: `explore --job` reads its done check reliably. An `http:GET <path>` done check is now read on the run's origin; every reading of one was `reading-unknown`, since the path was never made absolute. A goal run that ends without an accepted `done` (the judgment rejected every `done`, the run was blocked, or it ended on an answer) now takes its after reading at the end, so its job reads `achieved` or `not-achieved` from the app's state instead of `reading-unknown` with nothing read. A reading that truly cannot be taken stays `unverified`/`reading-unknown`, and the goal run's `job.reason` says why (`session-unavailable`, `page-replaced`, `check-unevaluable`).
- 81312e7: RC2 navigation lab fixes. A goal run that gives up below the no-route coverage floor, while it can still open an unopened page or try an untried safe control, is deferred (at most 3 times, each after an action) with a hint naming what is left; the floor still decides `no-route-found`. A page that hides a link to an unopened page or a button (a hover or collapsed menu) is now below the floor, so a hidden route never reads `no-route-found`. A blocked, stalled or exhausted goal run that does not end `no-route-found` names why in `noRouteShortfall`. With `--job`, a pass whose done check reads false now reports `goalOutcome: "failed"`, `goalReason: "done-check-failed"` (exit 1 as before), and a run that gave up or ran out of budget while its done check read false before and true after is the job done: `goalOutcome: "succeeded"`, exit 0 (job gates, the model's ending is advisory).
- Goal runs: landing again on a page state that the same forward step first reached (re-walking a wizard) is no longer a `ui-no-progress` hang; a step that drops back to an earlier state still is. A send that started nothing ends its action window, so a background read the page starts afterwards is not taken as the app working on the reply, and the quiet waits end the run on time (#241).
- 81312e7: `journey readiness` counts an achieved job only from a run whose own steps passed: an `achieved` done check on a quarantined or failed run reads `unverified` (`run-not-passed`). In `--mode replay` and `--mode prove` the `job` check now uses the job verdict of the replay readiness just ran (its done check read in a fresh session, as `journey run` does), never an earlier run's; a replay that read none is `unverified` (`replay-no-verdict`).
  
  `journey review` (and its JSON `job`) applies the same rule: a failed run's `achieved` done check shows `unverified — the latest run's own steps did not pass` (`run-not-passed`), not `achieved`.
  
  `journey shorten --budget` is parsed when the command line is (an integer from 1 to 500, else exit 64 with commander's usage error). Catalog contract v3's Journey schema now carries `metadata.done` (a Journey's own done check), which the runtime already accepts; v1 and v2 are unchanged.
- 81312e7: A mutation-proof receipt now records the target origin it ran on and, when known, the app version (`journey verify --app-version`, MCP `verify_journey` `appVersion`, or `JEVITATE_APP_VERSION`). A receipt from another target origin or app version reads stale, with `staleCause: "target"` or `"app-version"`. A receipt that names no target, or no app version while one is set now, still shows (a ○ note under `advisory`) and never counts for `require-sensitive`. Under `mutationProofPolicy: "require-sensitive"`, `journey verify` now exits 2 for a `sensitive` proof with `countsForGate: false`; under `advisory` it still exits 0. `journey review --env <name>` / `--base-url <url>` (MCP `review_journey` `env` / `baseUrl`) judges a proof's freshness for that target, resolved as `journey verify` resolves it, so a proof made on `--env staging` reviews fresh with `--env staging`; with neither, review judges the Journey's recorded site, as before.
- 81312e7: Over MCP, `verify_journey`, `journey_readiness`, `chain_journeys`, `demo_journey`, `run_load_test`, `run_exploration --fromJourney` and shorten now give a Journey the operator's `targets.json` `secretFields` only under the run-mode rule `run_journey` already follows: a promoted Journey, with an approval a person made on an automation-mode target, and an approval that still matches the Journey's content. A draft never gets them, and neither does a Journey edited after its approval (a stale approval): the run refuses with `E_SECRET_PARAM_OVER_MCP`, as `run_journey` does. `run_journey` and these tools now apply one shared rule. A `--secret-field` binding now goes only to origins a person or operator named (the run's origin, the environment's, `--allow`), never to an origin only the Journey's `allowedOrigins` lists. A navigate URL that would carry the secret anywhere else is refused `E_SECRET_ORIGIN_REFUSED` before any browser opens, and so is a field on such a page. The queue drain refuses a hand-edited queued call that carries a value for a declared-secret parameter (`E_SECRET_PARAM_IN_QUEUE`). It masks a failed call's error before storing it, and `get_mission_result` masks it again when it returns it. An upload refusal names a secret path by its `${name}` reference, not its value. An extracted value whose name holds a credential term and ends in a describing word (`apiKey_name`) is masked if it is credential-length. `verify-fix` masks `--param` values from 3 characters, and credential-named ones at any length. A declared 3–5 digit secret is masked even inside a longer number.
- 81312e7: A hold's checkpoint now masks a secret in the page address in every form it can take in a URL (including the strict encoding a navigate step sends and lowercase hex), and masks every value the run knows (a targets.json or vault binding, a fixture output, an extracted value) even with `JEVITATE_RUN_RECORD=off`. The `journey verify --mutate` native report is redacted for every secret its replays knew, not only secret parameters, is withheld if any URL- or JSON-encoded form remains, and is never written through a symlinked `.verify/reports`. A short secret equal to a code word (such as `ok`) no longer masks a run's `outcome`, verdict or error code, so the exit code is attached.
- 81312e7: A sign-in goal now ends succeeded when the app signs the run in but shows no sign-out or account control: a page that offered a sign-in control before the run typed its credentials, and offers none after, counts as the code-observed sign-in (the advisory scope check still decides that the whole goal is signing in). Before, such a run idled and ended blocked "answer not found" although the app had signed it in. That rule never applies while the page shows a sign-in error: an alert (`role=alert`, `aria-live=assertive`), an invalid field, or text saying the sign-in failed ("Incorrect email or password", "try again"). So a wrong password on an app whose home page swaps its Sign-in link for an error banner no longer reads as signed in.
- 81312e7: `journey run --allow <origin>` and `journey verify --allow <origin>` now let a step navigate to that origin under `--env` or `--base-url` (#803). Before, the origin check that runs before any browser read only the environment's own `allow` list. It refused the step with `E_ENV_ORIGIN_REFUSED` (exit 64), even though the help says `--allow` adds the origin. The refusal message now lists the `--allow` origins too, and it names `--allow` as a fix.
- 81312e7: A stale approval with fresh evidence is a human handoff, not a loop (#808). `journey readiness` (and `journey bundle`) list a strict-review item only a person's approval settles, such as "Changed since approval" or "Catalog links need re-review", under `awaitingHuman` with the owner's hash-bound commands, and no longer send you back to `journey review --strict`. Strict review and CI still fail until the owner approves; nothing is approved or waived. The `jevitate-promotion-ready` skill names this case.
- 81312e7: `import("@jevitate/cli")` works from an install (#815). The root export, `dist/index.js`, is now bundled like the `jevitate` bin; it imported the private `@jevitate/playwright`, which is never published, and failed with `ERR_MODULE_NOT_FOUND`. The release pack imports it in an empty prefix holding only the declared dependencies and checks that `buildProgram` and `versionString` are present and that it reports the bin's build identity.
- 81312e7: Strict review no longer blames an unchanged Journey for a proof from another jevitate version (#816). A stale proof now carries `staleCause`: `journey-changed`, `engine` (the Journey is unchanged, but the engine that recorded the proof computes its identity differently), `read-policy` (the target's `safety.readRequests` changed) `engine-unknown` (the receipt names no engine: written before 0.30.0) or `no-planner-identity`. Every verify receipt now stores `engine: {version, commit}`, so `engine` is read from the receipt, not inferred, and under `require-sensitive` a receipt that names no engine never counts. The review line, the policy reason and the readiness detail name the cause, and for `engine` recommend reviewing with the version that recorded the proof, or re-running `journey verify --mutate`. A mismatched proof still fails a policy that requires one.
- 81312e7: `journey verify` now explains a reloadThen-style end-state check that holds while the checks beside it fail (#817). End-state checks are judged one by one, so a check that held under a mutation was not blocked by the checks that failed beside it, and relaxing them would change nothing. The targeted refusal now says that, names every check that failed, and says when the held check is an absence check, which also holds on a page or view that has not loaded. `journey verify --plan` (and `--plan --json`, as `isolationNotes`) flags that shape before any browser opens: an end-state absence check that shares its mutations with other end-state checks. Verdicts are unchanged: such a check stays a `cascade` and the proof stays `inconclusive`. To prove it, first wait for content that shows the view loaded, for example by reopening the view in a later step.
- 81312e7: `journey verify --mutate` now saves its full redacted report before it prints anything (#818). If stdout is lost, for example when an SSH session drops, the per-mutation and per-assertion evidence is still on disk. The report goes to `.jevitate/journeys/.verify/reports/<id>/<stamp>-<sha256 prefix>.json`, mode 0600 in a 0700 folder. It holds the engine identity, the Journey and proof hashes, and the report itself. The canonical `.verify/<id>.json` receipt records the file as `nativeReport: { path, sha256 }`, and `--json` output carries the same field with an absolute path. A file is written once and never replaced, and the 20 newest per Journey are kept. If the report can't be written, nothing claims a file: the receipt and the output carry `nativeReportError` instead, and a warning goes to stderr. ### Minor Changes

- 6aba5d8: Opt-in `--action-deltas` (MCP `actionDeltas`, check-suite item option `actionDeltas`; `explore --strategy goal` and `usability`) records what each action changed on the page (#303). Off by default: no capture, no prompt or result changes, and no-progress works exactly as before. On: an accessibility snapshot before and after the action, the toasts and banners announced in between, the action's requests (method, path, status) and the URL and title, redacted first (registered secrets, password and secret-marked field values, credential-shaped values). Self-changing nodes (clocks, carousels, counters) are learned per route from no-action snapshots and dropped; the rest is ranked by closeness to the action and big changes are summarised. Code decides a verdict per action: `no-change` (nothing changed and no request was sent — the only verdict that counts toward a no-progress stop), `relevant-change`, or `inconclusive` (never progress or no-progress). Jev may label untied changes and propose per-route ignore rules, accepted only for nodes code saw change on their own. Each delta is attached to its transcript step (also in the `--json` result) and Recording step (`delta`), the result gains `actionDeltas` (verdict counts, overhead), the human output a `DELTA` line per recent step, and one bounded line goes into the model's step history; the expected change (navigation, the typed value, the sent message, a toggled state) is checked against it. A goal-run write that changed the page is re-checked once after a reload (a GET, never a re-post): `persisted: yes | no | inconclusive`. A report may quote text an action announced (a toast gone before the report).

Each session with extensions runs its own persistent Chromium context on a throwaway profile (headless: Playwright's full Chromium in new-headless mode, since the headless shell cannot load extensions) and proves each extension loaded before the run. Loaded extensions' `chrome-extension://<id>` origins — only those ids — are allowed, so a run can start at `--url chrome-extension://<id>/sidepanel.html` (a side panel, popup or options page is opened as a page in the same context) and the agent acts on its DOM; an unloaded id is refused (exit 64). A fixture step can authenticate as a named identity (`"auth": {"from": "cookies"|"localStorage", ..., "identity": "owner"}`) bound by `--fixture-identity <name>=<storageState>` (repeatable; `fixtureIdentity` over MCP and in a `check --suite` goal item) or by the origin's targets.json `personas.<name>.storageState`, separate from the mission's own session, so a fixture can mint an invite link as the owner while the mission opens it as a cold recipient. - 6aba5d8: Resource governance for shared machines (#205).
  
  - **Machine-wide browser cap.** At most `--max-browsers` jevitate processes have a browser open at once, across every jevitate on the machine. They share file slots under `~/.jevitate/run/browser-slots/`. A slot whose holder died, or that sent no heartbeat for 3 minutes, is reclaimed. The default is `JEVITATE_MAX_BROWSERS`, else cores/4, at least 2 and at most 6.
  - **Memory ceiling.** A run's browser memory (browser, renderers and helpers; Linux PSS, macOS RSS) is sampled every 2 s. Past `--max-browser-memory <MiB>` (else `JEVITATE_MAX_BROWSER_MEMORY_MB`, else 4 GiB or half the RAM), the session's page is closed. The run ends `inconclusive` with `failure.kind: "resource-limit"`, naming the measured value and the ceiling. It is never `crashed` and never a finding about the app.
  - **Adaptive throttling.** Above 2 load per core, under 1.5 GiB available, or under memory pressure, a new run takes half the machine cap and the default settle windows double. At 4 load per core or under 512 MiB available, a new run refuses with `E_HOST_STARVED` (exit 2) unless `--ignore-host-load`.
  - **Orphan cleanup.** Every launched Chromium carries `--jevitate-owner=<pid>@<start>`. Before each browser-driving command, browsers whose jevitate is gone are closed and stale slots cleared. The new `jevitate doctor [--cleanup]` reports and cleans on demand. Unmarked processes are never signalled.
  - **Results and MCP.** Results record all of this in `hostHealth.resources`: the cap, the slot, the most severe throttle level and every change, the ceiling, peak memory, and any resource limit. The MCP tools that launch a browser take `maxBrowsers` and `maxBrowserMemory`.
  - **Turning it off.** `JEVITATE_RESOURCE_GOVERNANCE=off` turns off the automatic parts.
- 6aba5d8: New built-in agent skill `jevitate-test-campaign` (#292), installed by `jevitate init` with the others: how to plan and run an end-to-end release test campaign — preflight, a jobs-to-be-done catalog with goal specs, discovery runs that draft Journeys, journey-anchored adversarial/exploratory missions, a small coverage pass, full-stack log evidence, collect-then-fix with `verify-fix`, the ledger and regressions, triage by exit code, budgets, `check` suites in CI, and the release gate. Includes job-spec and issue-register templates.
- 6aba5d8: UX findings are claims verified by code (#198). `jevitate ux` and `explore --strategy usability` no longer let the rubric report findings on its own. A finding comes from one of three places. A guard probe, which is opt-in (`--probe-guards`, MCP `probeGuards`, suite `probeGuards`). Without it nothing is clicked and guard claims are reported unverifiable. With it, the live run clicks each control the safety policy calls destructive, once per page, on a fresh page. It aborts every non-GET request and every request whose URL, query, RPC name or body names a destructive verb, whatever the method. It refuses a page with an open WebSocket or EventSource or a controlling service worker. It cancels any confirm, never clicks inside a dialog, and closes the page as soon as one appears. It records whether a native confirm, a page dialog or a confirmation page came first and which requests the click attempted; none reach the server. The product facts: `.jevitate/product.json` or `--product <file>` lists plans and prices, trial lengths, key journeys and each page's intended next step; a price or trial on screen that contradicts them is a `fact-conflict`, and a missing or disabled next step is `next-step-unclear`. Observed friction no run signal explains: Jev categorizes it with a claim type from a closed list (or not-a-problem) and a target control from the page's real controls, bounded under the choice cap. Code verifies every claim; one that fails is dropped and counted in `report.claims`. The same claim type on the same page and control merges by code, and Jev's one duplicate choice merges a finding into an earlier one as `contributing`. Two Jev yes/no questions, "do we need this?" and "do we need this to complete and ship this feature?", grade each finding; code maps them to actionable / relevant-minor / generic / wrong with cutoffs from `assets/ux-claims.json` (`finding.grade`). Finding text is built from templates over the verified fields; `--polish` (opt-in) rewrites the recommendation with one generation call. Live findings get a cropped, secret-masked screenshot with the cited control boxed (`finding.screenshot`). The judge stays text-only (the Jev SDK takes no images). The product facts file is validated strictly, and an invalid one is refused with `E_UX_PRODUCT_INPUT` (exit 64) before a browser opens. The guard probes are saved in the evidence sidecar, so offline review verifies the same claims. All output changes are additive (schemaVersion 1); see docs/ux-findings.md and the upgrade notes.
- 6aba5d8: Vertical-clipping signal (#302). Viewport runs now flag text that no scroll position shows: text cut off by its nearest `overflow: hidden`/`clip` box whose content is taller than the box (`overflow-hidden`, attributed to the box), and text that spilled out of a too-short container above the page top (`above-page-top`, attributed to the text's element — e.g. a `flex-wrap` chip centred in a fixed-height header). It runs alongside horizontal overflow under the same gate (`--viewport`/`--device` narrower than 1024px, or `--check-overflow`) and is reported the same way: a `vertical-clipping` defect in coverage/exploratory/adversarial runs and a `signal-vertical-clipping` finding in the usability review, one per element (route + element fingerprint). Intentional truncation (`line-clamp`, `text-overflow: ellipsis`), sr-only/collapsed/invisible text, skip links, scroll containers and the page root are not reported; `--ignore-overflow <selector>` excludes the rest. See docs/exploration.md.

### Patch Changes

- 6aba5d8: Adversarial runs notice when an action switches the signed-in identity (#300), such as a "Continue as demo" shortcut on a login page. The run takes a baseline from the session's auth cookies and auth-named storage, kept as hashes only and never raw values; a JWT is compared by its subject claims. After each settled action it checks again. On a switch, that step's invariants (`userInvariant` and the declared spec) are not judged, its pending `before` snapshot and queued `never.response` hits are dropped, and the control is never picked again. The run then goes back to the start URL in a fresh session from the original storage state. Every switch is listed in `identityChanges` (`{step, action, url, route, reason, restored}`). When the original identity can't be restored, the run stops `inconclusive` with `stop: "identity-changed"` and `failure.kind: "identity-changed"`.
- 6aba5d8: Adversarial `boundary-submit` asks whether a field's input is rendered as markup (#301). Its values now include two inert canaries with a fresh random token per submission: an HTML-injection canary (`<i data-jev-canary="T">jevT</i>`) and an attribute-break canary (`jevT" data-jev-canary="T`). They have no script, event handler or `javascript:` URL. The values also include an oversize (~100 KB) value, and the unicode value gains an RTL override and zero-width characters. Detection is DOM inspection only: after the submit settles, and again after a plain GET of the same in-scope page, the run looks for an element carrying the canary attribute. A hit is a `markup-injection` defect with `markupInjection: {field, payload, submittedOn, renderedOn, afterSubmit, afterReload, stored}` (stored vs reflected). A canary shown as escaped text is not reported. `verify-fix` returns `inconclusive` for this kind; re-run the mission instead.
- 6aba5d8: Find-out grounding (#236, #234, #238). Numbered-list markers at a line's start are formatting, never stated figures, and a claim's inflected word is said by its quote ("not subscribed" over "No subscription"). A multi-line quote grounds when every line is on the same observed page in order (a list of section headings); otherwise the rejection says what a quote must be, and an identical rejected re-report is named as a repeat. A goal that asks whether something exists may now be answered "none exists": when the generator finds no answer, code accepts `not present — none of the pages seen shows it (pages seen: …)` (`answer.absent: true`, `answer.searched`) once the run has seen at least half of its top-level navigation (never fewer than 2 pages; 2 distinct pages without a navigation); below that floor the report is refused naming the unseen pages, and a run that ends there is `inconclusive` (`failure.kind: "insufficient-coverage"`), never `blocked`/`defects-found`.
- 6aba5d8: Find-out guard (#253, #270). A form submit is judged by the requests it sends, not by its shape: a lookup form's "Load" that only reads (GET/HEAD, a `Get*`/`List*` RPC, `--read-rpc`) is clicked, and a submit that writes is blocked at the network (a native form POST is answered `204` in the browser, so the page stays put). A goal with no `--success` whose text asks for a change is no longer read-only but never destroys on its own words: a destructive control is refused (no goal-word lift) and a destructive write request (`DELETE`, a `Remove*`/`Delete*`/`Revoke*` RPC, a `/remove`-like path segment) an action fires is blocked, unless `--allow-writes` or `--allow-destructive`.
- 6aba5d8: Goal runs that invite (#235). A "Send <thing>" control in the paid category ("Send invite", "Send email") is now the goal-asked exemption when the goal orders the thing itself at a clause's start ("Invite a teammate…", "…then invite Bob") — as `explore --help` documents; a mere mention ("report the invite's status") still asks for nothing. When every `--success` check is a `reloadThen` (judged only after the run), the in-run check evaluates nothing: it still grounds the model's own `done` provisionally, but no longer turns a `blocked`, a sign-in or the "already met" signal into "goal already met" — the run ends `blocked`, and a model that gave up after a safety refusal names that refusal in the reason.
- 6aba5d8: Goal runs stop looping on actions that can never make progress, and stop misjudging it. Controls behind an open modal and controls no scroll can bring into view (a closed panel translated off-screen) are no longer offered; a target that fails twice as covered or unreachable is withheld, and five failed actions in a row end the run naming the overlay (#272, #294). A `select` never re-chooses the selected option or a placeholder, and option matching tolerates dash spellings (#273). Retyping a field that changed nothing but its own value is no progress: a search box is submitted with Enter, any other field ends the run as stuck (#242). A `send` that started no request and changed nothing is a failed send, and background polling no longer keeps a reply wait alive (#241). A model `blocked` before any action is refused and, if it insists, ends `inconclusive` rather than `defects-found` (#237). A disclosure `<summary>` is a control, and controls the goal names survive the candidate cap (#287). Steps that were refusals or scrolls the app answered never make an app `ui-no-progress` hang (#276).
- 6aba5d8: A goal that asks for a report needs its answer (#286). When the goal asks the run to report what it found ("Finish by reporting the price shown") and `--success` checks are given, the checks holding no longer end the run ("goal already met" under `--success-when held`) and are not the whole verdict: the model is told to end with `report`, a `done` is rejected with that reason, and without a grounded answer the run does not succeed — `checks` gains a failing `report (the goal asks for a grounded answer)` entry. A check satisfied mid-run by an unrelated page's load-time request (a quote fired on load) previously ended such a run `clean`/`succeeded` with no price reported.
- 6aba5d8: Waits are no longer misread as hangs, and missions no longer stall on busy pages. A wait the page documents ("usually takes less than a minute") and a busy indicator the app visibly keeps working behind (live progress, a job poll) are waited out within `--job-wait-ms` (a documented duration can raise it), while a spinner over a silent page is still a hang and a deferred hang names the budget (#258, #288). A save that writes and returns to an earlier route is progress (#289). The feature mission treats its seed page as in scope and re-queues a seed that re-renders on reset (#277), and perception is bounded on large pages (#278). A renderer that freezes mid-perception ends `inconclusive` (`failure.kind: "stalled"`), never a crash attributed to jevitate (#296).
- 6aba5d8: A long-pending in-flight request is no longer forgotten (#283). `requestMade` matches a request once it is sent, whether or not its response has arrived (a gRPC-web/Connect unary call the server holds open while a job runs); `responseStatus` judges only answered requests. A write one of the run's clicks fired stays tracked until it ends, even after the settle rule treats it as a long-poll: a `wait` observes it within the job-wait budget ("POST /… (sent by an earlier click) is still in flight") instead of reporting "nothing is pending", and a model `blocked` is deferred the same way. It also stays in `sideEffects` and in the repeated-side-effect guard.
- 6aba5d8: Paid controls with a live estimate (#280, #279). A goal asks for a `--paid` control by its action word: a trailing estimate ("Confirm analysis (≈ 4–10 credits)") and confirmation words ("Confirm", "and") are ignored, so "analyze this text" asks for "Confirm analysis"; the built-in label-length cap ignores the estimate too. The budget guard reads a numeric `dom` estimate at its worst case: a range such as "≈ 50–90 credits" counts as 90 (an explicit `number: { index }` is kept).
- 6aba5d8: A chat's next message is awaited while its own request is still in flight: the run's earlier turns' writes to the same endpoint are not background polling, a request held past the long-poll threshold still counts, and a later `wait` on the turn sees it. Background polls are told apart over the last minute, not only since the last step. A `--settle-ignore`d beacon is never an action's effect or a sign that a busy app is working (#241, #283, #284, #288).
- 6aba5d8: A report no longer grounds on the run's own unsaved input (#239). A form field holding a value the run itself typed is not evidence of what the app recorded until a click the run made fired writes that all answered 2xx; such a `control-value` quote is rejected ("the run's own typed input in …, never saved"). A goal whose imperative is a write ("record / save / create / add / invite / submit / send / post / publish / register / book / schedule …") is not settled by a find-out `report` before any write of the run succeeded — the report is rejected with that reason, so "record a decision" can no longer end `succeeded` with nothing saved.
- 6aba5d8: Runs check their AI keys at startup (#291). A run that uses the live AI (`explore --real`, `check`, `journey run/annotate/demo --real`, `demo`, `ux`, `mission run`) makes the same live, non-billable auth call as `ai status`, once per key per process, and stops with `E_AI_SETUP_REQUIRED` (exit 64) when a provider rejects a key, naming the key, its provider and a misplaced-key hint (never the value). An unreachable provider does not block; `JEVITATE_NO_KEY_VERIFY=1` skips the check for offline CI; `--fake-ai` never makes it.
- 6aba5d8: The repeated-side-effect guard counts only the app's own writes (#274, #284). A write to a third-party origin (a vendor's telemetry or `csp-report` beacon, Stripe.js's `POST https://m.stripe.com/6`) or a request matched by `--settle-ignore` is still listed in `sideEffects` (third-party ones marked `thirdParty`), but it no longer makes a safe control (a menu, a nav link) unclickable a second time. A repeated first-party write is still refused.
- 6aba5d8: Console errors raised inside a cross-origin third-party iframe are no longer reported as the page's own defects (#297). Every `console-error` signal now records the `frameUrl` of the frame that logged it (its document, or the frame that loaded the logging script). One from a frame whose origin is third-party to the run (off the `--allow` origins' sites, as for #194's beacons), such as a payment vendor's iframe logging its own CSP violations, is reported in `advisories` with `thirdPartyFrame` (the vendor's origin) and never gates the outcome. It has one fingerprint per vendor and message, whichever route embeds it. The app's own console errors still file as defects.
- 6aba5d8: `explore --type-fixture '<label|testId|type|id|name>=<value>=<file>'` (#281; MCP `run_exploration` `typeFixture`, its path confined like every MCP path). When a goal run types into a matching field, code types the file's exact text verbatim (line breaks kept, never paraphrased by the model, never capped); the model sees only `«fixture:<file name>»`. The file must exist and be UTF-8 text of at most 256 KiB. The Recording keeps the text for an exact replay, or `{ redacted: true }` when it contains a registered secret.
- 6aba5d8: Quoted goal text is typed verbatim (#281). A passage the goal quotes in double quotes as the text to type — right after a typing verb ("type", "enter", "paste", "write", "import", "insert", "post", "reply", "add", "use", "with") or a `text:` / `content:` / `body:` / `message:` lead-in, spanning several lines or 6+ words — is typed by code into a textarea / rich-text field without asking the model, its line breaks kept and never cut by the free-text cap (that cap is for generated essays). A goal can carry a file's text this way (`--goal "Import this text: \"$(cat note.txt)\""`). Before, the model paraphrased it ("Click here to learn more…" became "Discover more…") and the paragraphs were collapsed.

- f75b99c: One CLI contract for every command (#210). **Exit codes:** `0` ok · `1` defects (defects found, a gating finding, still reproduces) · `2` inconclusive (the run or command could not finish: inconclusive/crashed, an errored `check` item, a queued mission that could not run, an unexpected error) · `3` hang · `4` intermittent · `64` usage/input error, where nothing ran · `130`/`143` killed. Before, a goal result put `succeeded`/`failed`/`exhausted`/`blocked` in `missionOutcome`, against docs/outcomes.md and `explore --help`. Every run samples the host's health (the browser pool's admission thresholds, load average per core, the driver's event-loop lag, and the render trend against the run's own baseline), and every result now carries `hostHealth` (peak load per core, minimum free memory, peak event-loop lag, slowest render, starved steps) and `environmentDegraded`. - f75b99c: HTTP 5xx is a hard-signal defect in every strategy (#208). Goal, feature, coverage/exploratory and usability runs now record a 5xx from the app's own origins as an `http-5xx` defect in `defects`, with the same fingerprint the adversarial strategy gives it (endpoint pattern + status), so `verify-fix` replays it the same way. A goal run whose success checks held but whose run hit a 5xx ends `defects-found` (exit 1), never `succeeded`: `assertionPassed`/`checks` keep the checks' verdict and `reason` names the failing request (`PUT /demo/api/profile → 500`). An adversarial run whose start page itself answers 5xx reports that as an `http-5xx` defect (`defects-found`, `stop: "not-rendered"`) instead of an inconclusive "not rendered". A 5xx from a third-party origin (#194) is not the app's defect, in every strategy. In a usability run the defect is listed with `advisory: true`, like its `server-log` defects.
- f75b99c: Journeys are environment-free (#247). Name the places your app runs in a committed `.jevitate/environments.json` (`{ "<name>": { "baseUrl", "allow"?, "fixtures"?, "hooks"? } }`; `jevitate init` writes an example once and never overwrites it) and choose one at run time with `--env <name>` or `--base-url <origin>` on `journey run`, `regression run` and `load run`, or with `env`/`baseUrl` on a check-suite Journey item. The Journey's recorded same-origin URLs move onto the environment's `baseUrl`, and the run's allowlist is the environment (`baseUrl` + `allow`): a step on any other origin is refused with exit 64 before any browser opens, and so is an unknown `--env` (the message lists the known ones). The file never holds secrets or sessions: a `storageState`/`secret`/`password`/`token`/`cookie`/`credential` key is refused. Per-environment sessions and secret fields stay in `~/.jevitate/targets.json`, keyed by the environment's origin (`storageState`, `secretFields`, and new `personas: { "<name>": { storageState?, secretFields? } }`). Without `--env`/`--base-url` a Journey runs on its recorded site exactly as before.
- f75b99c: Journeys can now say why, not only what (#246). Every new field is optional and additive, so an existing Journey validates and runs unchanged. At the Journey level they are `metadata.goal`, `persona`, `role`, `preconditions` (linked to fixtures and hooks), `successCriteria` (each with an optional code `check`) and `parameters` (`secret: true` marks a value for redaction). Each step gets `objective` and `expectedResult`. A new command, `jevitate journey annotate <id> --real|--fake-ai`, replays the Journey, reads the redacted page before and after each step, and drafts the missing objectives and expected results, plus the goal and success criteria, into `.jevitate/journeys/.drafts/<id>.annotations.json`. It never writes the Journey. `journey annotate <id> --approve` is the human gate: it shows the diff, then writes the reviewed draft. It refuses a draft made against a Journey that has changed since (`E_JOURNEY_ANNOTATIONS_STALE`, exit 64). A secret parameter's value is redacted in the `journey run` output, in annotate's evidence, drafts and output, and in anything sent to a model. `journey run` also reports how many steps lack an objective; this is informational and never fails. See docs/journeys.md, "Journey format reference" and "Annotate a Journey".
- f75b99c: Truthful outcomes (#209) — a published contract change. A run that proved nothing is never `clean`, its reason is named, and every defect is in `defects`:
  
  - **Goal:** a new `failed` outcome (exit 1, folds onto `defects-found`) for a run whose model said `done` but whose independent success check then failed, with `failure.kind: "success-check-failed"` naming the check. It was `blocked`, which now only means the loop gave up. A run whose only failing checks are vacuous (#202) is now `inconclusive` (exit 2), with `failure.kind: "vacuous-check"` instead of `blocked`. Its check detail no longer ends with "held on the final page". While a check is still pending (a `reloadThen`, or a check that has held since before any action), the transcript records the model's `done` as "accepted provisionally" instead of "goal verified by success-condition".
  - **Usability:** a review whose job was never completed is `inconclusive` with `failure.kind: "job-incomplete"`. It used to be `clean`.
  - **Feature:** a run whose every exercised control was unrelated to the feature (all `relevance=0`) is `inconclusive`, the same as the chrome-only case. Both the frontier `outcome` and `failure.kind` are `insufficient-coverage`. It adds `coverage.relevantActionsExercised` and `coverage.featureWords`.
  - **Adversarial:** when every target control is refused by the safety policy, the run stops early with the new stop reason `targets-refused` and reports `coverage.controls.refused`. The failure names the refused controls and the flags that permit them (`--allow-destructive`, removing a `--deny`, or `--paid`/`--deny` to reclassify a control).
  - **Coverage / exploratory:** each ending now has one name. The frontier outcome and the failure kind are both `insufficient-coverage` (#203's `insufficient-exploration` is renamed), and `exhausted` now means the frontier was fully covered. Links in the page body count as coverage, while only chrome links (`<nav>`/`<header>`/`<footer>`, or links repeated across pages) count as global navigation. The shortfall now says how to reach `clean`.
  - **Defects:** a coverage run's frontier defects (`horizontal-overflow`, `judgment-flagged-state`) are now also in top-level `defects`, each with a `fingerprint` and `kind`.
  - Goal outcomes map to exit codes in one place: `GOAL_OUTCOME_FOLD` / `outcomeExitCode()` in `@jevitate/domain`.
- f75b99c: One versioned result schema across explore strategies (#195). Every goal, coverage, exploratory, adversarial, feature and usability result now carries `schemaVersion: 1`, `strategy`, `missionOutcome`, `exitCode`, `defects`, `hangs`, `recordingPaths`, `transcriptPath`, `resultPath`, `target` and `engine`, filled the same way by every strategy. `defects` now holds every defect, `server-log` ones included; a usability run's server-log defects are marked `advisory: true` and still never gate its outcome. `recordingPaths` is always an array. A new finding ledger (`jevitate ledger add|list|verify`) keeps the repro material in the repo, so `jevitate verify-fix <fp>` works from a fingerprint alone. `regression capture` accepts failed success checks, network checks and declared-invariant violations as its oracle, never the engine's own refusals, and `regression run <id>` replays a committed regression.

### Patch Changes

- f75b99c: Every command refuses unusable input the same way (#218, the #210 follow-up). **Exit 64, not 2 or 1:** numeric flags are parsed while the command line is parsed (`explore --max-actions abc`, `verify-fix --replays abc|0`, `--stall-timeout`, `--hang-replays`, `--reply-*-ms`, `--hook-timeout-ms`, `load run --concurrency`, `ui --port`, …); `regression run <unknown id>` (`E_REGRESSION_NOT_FOUND`), `regression capture --from <missing file>` (`E_REGRESSION_ARGS`), `ux <missing or invalid recording>` (`E_UX_INPUT`, was `E_UX_RECORDING`), `baseline show <unknown tag>` (`E_BASELINE_NOT_FOUND`) and `invariants validate <unreadable file>` (`E_INVARIANTS_INPUT`, was exit 1). `check` now refuses up front a suite item whose start URL (its own, else the target's) is off the target's allowlist, and a `verifyFix` whose fingerprint is not in its result — they used to fail at runtime as an errored item (exit 2). **Output:** without `--json`, every refusal is `error <CODE>: <message>` on stderr with nothing on stdout — `journey run`, `ux`, `regression run|capture`, `diff`, `baseline`, `report`, `site`, `recording`, `source`, `mission`, `ai`, `mcp` and `invariants validate` used to print the JSON envelope on stdout. With `--json` the envelope is unchanged, and a command line refused while parsing (an unknown flag, a bad number) now also prints one, coded `E_<COMMAND>_ARGS`. A test walks every registered command's refusal paths so a new command cannot regress.
- f75b99c: Find-out answers must answer the question (#223). An answer is now rejected when its quote is only an action or label name (a button, a form field's label, or a navigation/header/footer or repeated link; a link in the page's content, such as an item title in a list, still counts as content), or when it sits on an error page (the document answered HTTP 4xx/5xx, or its heading or title says not found / 404 / error). Such a run ends "answer not found". An independent Jev check, "does this quote answer the goal's question?", can veto an answer that code grounded, but it can never approve one on its own. A `<textarea>` value, or the text of a contenteditable field, now grounds an answer as a form field value, the same way an input's value does.
- f75b99c: Find-out goals answer from ordinary page text and form values (#207). A read-only find-out goal's decisions now carry the page's visible text (redacted, bounded), so an answer in a table cell or heading is seen and reported; a model `blocked` on such a goal first becomes one grounded report attempt on that page state (never an answerless "goal already met"). A form control's current value (never a password / one-time-code / bound secret field) is a grounding source: evidence records `source: "control-value"` and the control, while page-text quotes record `source: "page-text"`. A run whose report found no answer ends "answer not found (pages seen: …)" instead of a generic no-progress / blocked reason, and a literal "null" answer counts as no answer.
- f75b99c: A state flagged only by Jev's judgment is advisory (#214). In coverage and exploratory runs, a `judgment-flagged-state` defect now carries `advisory: true` in `defects` and `coverage.defects`. It keeps its repro Recording, so `verify-fix` can still replay it, but it never sets `missionOutcome` or the exit code on its own. A run whose only finding is a flagged state now ends `clean`, or `inconclusive` when it exercised too little; before, it ended `defects-found` with exit 1. The run is `defects-found` only when an independent code oracle confirms a defect: an HTTP 5xx, a horizontal overflow, a declared invariant or a server-log defect. `check` and `report` read a flagged state as an advisory finding, the same as before, and the human summary counts it as advisory.
- f75b99c: Security: a profile name or regression id can no longer escape its directory (#221). `profile create ../x` used to create a directory outside the profiles folder (profiles hold browser sessions). Profile names (`profile create|status`) and regression ids (`regression capture --id`, `regression run <id>`) must now be one safe path segment — 1–128 letters, digits, `.`, `_` or `-`, starting with a letter or digit, no `..`, `/`, `\`, NUL or absolute path — checked by one shared helper that also verifies the resolved path stays inside its root. A refusal is `E_INVALID_NAME`, exit 64.
- f75b99c: Usability runs recognise a completed save, and honour `--success` (#225). **Done-recognition:** the goal judgment now sees the page's form fields and their current values (a field's value is never in the page text, yet it is where a form shows what was saved — non-secret values only, never a bound secret or a message composer). Code evidence is preferred over the judgment's probability: when the run submitted its typed values, every write the submit fired finished 2xx, a success notice ("Saved") and no failure shows, and the page still displays each saved value, `done` is accepted as `verifiedBy: "save-signals"` — if the advisory scope head says the whole goal is that save (the #188 sign-in pattern). A save answered by a 4xx/5xx is never such evidence, even when the page says "Saved". **`--success` for `--strategy usability`** (and a usability suite mission's `success`/`successWhen`, `allowVacuousChecks`): an independent completion check with a goal run's semantics — it grounds `done`, the #202 vacuous rules apply, and the verdict folds like a goal run's (`goalOutcome`, `checks`, `checkWarnings` in the result; a failed check is `defects-found`, exit 1). It used to be silently ignored; an unparseable one, or `--success-when`/`--allow-vacuous-checks` without one, is now refused (64). A usability run whose check fails reports `failure.kind: "success-check-failed"` naming the check, and stops as soon as the job is judged done on the page but the check failed, instead of spending the whole action budget. `--strategy coverage|exploratory|adversarial` and `--feature` now refuse `--success`, `--success-when` and `--allow-vacuous-checks` (64, `E_EXPLORE_ARGS`) instead of silently ignoring them; suite items of those strategies already refuse them.
