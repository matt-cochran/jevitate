# Jevitate 0.30.0: evidence and trust

Status: design for 0.30.0, written 2026-11-06 against the code about to ship as 0.29.0
(`integration/2026-11-04-0.28.3` at `266ccf9`). Nothing here is implemented. The plan that
executes it is `docs/design/0.30.0-plan.json` (cpm-planner line `jevitate-0-30-0`).

Issues #800, #792 and #812 are designed together because they share one decision: **what evidence
Jevitate trusts, and from whom.** The other 0.30.0 issues (#793–#799, #801, #802, #807, #810) are
consumers of that decision, and each gets a section or a line in the coverage table at the end.

## 0. The decision in one page

Jevitate exists "to prove that users can meet their objectives within the application". A result
therefore has to answer two different questions, and 0.29.0 answers them with one word, `proven`,
which misleads: a `proven` mutation proof says the Journey's checks noticed a changed step, not
that the job got done.

From 0.30.0 every result separates:

| Question | Field | Values | Decided by |
|---|---|---|---|
| Did the user reach the goal? | `job.attainment` | `achieved`, `not-achieved`, `unverified` | a **done check** read by code, false before the run and true after it, read back in a fresh session (#800) |
| Would our checks notice a failure? | `checks.verdict` | `sensitive`, `insensitive`, `inconclusive` | a **mutation proof**, trusted only on a target that can be reset (#792 target configuration) |

Both verdicts are computed by one pure function in a new private package, `@jevitate/adjudicator`,
from one versioned **evidence record** that every run writes (#812). Jev's judgments are in the
record, marked advisory, and the function's output never depends on them: that is the invariant
"Jev advises, independent code adjudicates", and it is a test, not a sentence.

Why `achieved` must rest on a check and never on judgment alone: on the navigation lab, a
judgment-only pass was wrong 8 of 20 times, and `looks-done-wrong-page` passed falsely 8 of 10
(`.delivery/nav-lab/remediations.md`, "Baseline at n=10"). No prototype lowered it; a generated
postcondition sentence raised false rejects by 37 points on clean cases. The only remaining route is
a code-evaluated done check, which is what #800 is.

Why mutation proof is demoted from "the" evidence to a strength measure: on Journeeze, no promoted
Journey reached `proven` on either 0.28.0 or the candidate (`.delivery/rel-0283/experiments/journeeze-report.md`),
annotated proofs cost 1.6–2.4x the time of 0.28.0, and the TRIZ pass concluded that a mutation proof
on a system you cannot reset is "not reconcilable in general"
(`.delivery/rel-0283/triz/mutation-uncontrolled.decision.md`). So the proof keeps its exact
semantics, is renamed to say what it shows, and is only counted as a strict gate on a target whose
configuration says it can be reset.

What a developer new to this needs to hold in mind: **a run gathers; the adjudicator judges; a
person decides what to trust by writing target configuration.** Nothing an agent can do over MCP
changes which of those three it is.

## 1. Inputs and the numbers this design rests on

- Navigation lab (`.delivery/nav-lab/baseline.md`, `remediations.md`, `implementation-plan.md`):
  39 cases, 10 replicates each on the second pass, 1,440 cells for $0.60. Route-exists failures
  30.5% (67/220). Every no-route or wall run ended exit 1 `defects-found` (33 of 39 misattributed
  after excluding the two injection-forward arms whose defect ending is correct). Proven on the lab:
  wall boundary 10/10, session boundary 10/10, return to an earlier state with untried controls
  28/30 against 0/30, off-allowlist and new-tab boundary 10/10 each. Refuted: refuse-blocked
  (0/30), untried streak (4/10), saturation stop, page text on goal runs (follow rate rose to
  10/30), generated postcondition (+37 points false rejects), no-route reason (precision 56%),
  gesture (0/10), opaque boundary (fires on any canvas; untested beside a working route).
- Judgment-only pass: false 8 of 20 (navigation goals), 8/10 on `looks-done-wrong-page`.
- Journeeze comparison (`journeeze-report.md`): plain runs ratio 1.01; annotated proof 1.60–2.42x;
  as-recorded Journeys give 0 mutation pairs, so no proof at all; five defects, two new in the
  candidate (a `no-store` body that never fires `requestfinished` reads as an open write; a taint
  blames `skip:2` when only the independence replay ran).
- Security findings (`security-final6.md`, six passes): the High findings were in *evidence
  gathering* (a write dropped when any frame starts loading, H1; a kept body answering a different
  write, H2), in *name matching* (H3, R5), in *origin binding* (M1, R1, R2, D1–D3), in *model
  exposure through heal and annotate* (R3, D4), and in *masking after a cut* (E2, F2). None were
  in verdict rules. #812's own "Limit" paragraph says the same. This design treats gathering as the
  thing to make typed and testable, and keeps the verdict rules small.
- 0.29.0 bars and accepted limits (`finish/risk-bars.md`): false `proven` 0 of 90; secret
  capability over MCP accepted as a limit; forged `provenance.channel` by an agent with file
  access accepted as a risk; judgment-only navigation passes to be warned about, fixed in 0.30.0.
- TRIZ (`state.decision.md`, `speed-quality.decision.md`): the bypass route, "answer the job
  question inside one run with a done check", is the best fit for both the state and the speed
  contradictions; "mutation proofs only on a resettable target" is the natural fit for #792.

## 2. Contract 1: the evidence record (#812, #800)

### 2.1 Decision

One versioned record, `RunEvidence`, written by every Journey run, goal run and mutation proof,
and the only input the adjudicator reads. It is value-free by construction: its fields are enums,
counts, shapes, hashes and keyed digests. The only free text is `reason` strings that code
templates produce. Every quantity a gatherer may fail to establish is typed `Known<T>`, so
"unknown" is a different value from "zero".

The types below are the contract. They will live in `packages/adjudicator/src/evidence.ts` as zod
schemas with these inferred types; the JSON written to disk is the parsed form.

```ts
/** A fact the gatherer either established or explicitly could not. Never undefined. */
export type Known<T> =
  | { readonly known: true; readonly value: T }
  | { readonly known: false; readonly reason: UnknownReason };

export type UnknownReason =
  | "page-not-watched"      // the browser did not let the replay watch the page in time
  | "page-replaced"         // the page or context changed while the fact was being read
  | "session-unavailable"   // a fresh session could not be opened (auth, network)
  | "check-unevaluable"     // the check names a target that does not exist on this page
  | "replay-stalled"        // the replay never finished closing
  | "not-gathered";         // this producer version does not gather this fact

export interface RunEvidence {
  readonly schema: "jevitate.evidence";
  readonly version: 1;
  readonly producedAt: string;                // ISO 8601, from `clock`
  readonly producer: { readonly jevitate: string; readonly commit?: string };
  readonly subject: EvidenceSubject;
  readonly run: RunContext;
  readonly steps: readonly StepEvidence[];
  readonly writes: WritesEvidence;            // the whole run's writes, every replay included
  readonly doneCheck?: DoneCheckEvidence;     // §3
  readonly mutation?: MutationEvidence;       // present only on `journey verify --mutate`
  readonly boundary?: BoundaryEvidence;       // §6.2
  readonly judgments: readonly AdvisoryJudgment[]; // Jev; never consumed for a verdict
  readonly notes: readonly string[];          // code-templated reasons, for people
}

export interface EvidenceSubject {
  readonly kind: "journey-run" | "goal-run" | "mutation-proof";
  readonly journey?: { readonly id: string; readonly hash: string };   // journeyContentHash
  readonly job?: { readonly id: string; readonly hash: string };       // catalog content hash
  readonly goalDigest?: string;               // keyed digest of a goal sentence; never the text
}

export interface RunContext {
  readonly mode: "test" | "automation";       // §5; decided by target configuration
  readonly channel: "cli" | "mcp" | "queue";
  readonly target: {
    readonly origin: string;                  // canonical origin only, never a full URL
    readonly environment?: string;            // name in environments.json
    readonly trust: TargetTrust;              // §5.2
  };
  /** Keyed HMAC over the non-secret parameters (sorted name=value). Secret parameters contribute names only. */
  readonly paramsDigest: string;
  readonly secretParamNames: readonly string[];
  readonly approval?: { readonly channel: ApprovalChannel; readonly contentHash: string };
}

export interface StepEvidence {
  readonly index: number;                     // 1-based, as `step:<n>` site keys
  readonly kind: string;                      // the recorded step kind
  readonly outcome: "ok" | "failed" | "skipped" | "not-reached" | "refused";
  readonly postcondition: "held" | "failed" | "none" | Known<never>;  // Known<never> = unknown with a reason
  readonly writes: Known<number>;             // writes this step sent
  readonly refusal?: RefusalCode;             // E_RUN_REFUSED_*, E_SECRET_ORIGIN_REFUSED, …
}

export interface WritesEvidence {
  readonly sent: Known<number>;
  readonly answered: Known<number>;
  readonly aborted: Known<number>;
  /** Still open when the run or replay closed. `{known: true, value: 0}` means "no write open"; `{known: false}` means we could not tell. */
  readonly openAtClose: Known<number>;
  readonly shapes: readonly WriteShape[];     // value-free, as journey-run-record.ts already writes
}

export interface WriteShape {
  readonly step: number;
  readonly method: string;                    // GET/POST/…/OTHER
  readonly path: string;                      // literal route text only; parameters masked
  readonly origin?: string;                   // only when off the Journey's own origin
  readonly count: number;
  readonly status: Known<"2xx" | "3xx" | "4xx" | "5xx" | "aborted" | "unanswered">;
  readonly refused?: true;
}

export interface MutationEvidence {
  readonly plan: {
    readonly mutations: readonly { readonly id: string; readonly kind: MutationKind; readonly step: number; readonly param?: string }[];
    readonly pairs: readonly { readonly site: string; readonly mutation: string; readonly declared?: true }[];
    readonly sites: readonly { readonly site: string; readonly check: string; readonly required?: true }[];
  };
  readonly replays: readonly ReplayEvidence[];
  readonly restore: "ok" | "failed" | "none";
  readonly isolation: Known<"isolated" | "state-crossed">;  // the independence replay's reading
}

export interface ReplayEvidence {
  readonly ordinal: number;
  readonly role: "base" | "independence" | "mutated" | "relaxed" | "targeted" | "control" | "at-base-time" | "rerun" | "closing";
  readonly mutation?: string;                 // the mutation id, for every role but base/independence/closing
  readonly relaxedSites?: readonly string[];
  readonly outcome: "passed" | "failed" | "error" | "stalled";
  readonly failedSites: readonly MutationFailedSite[];   // as today, plus `evaluated?: true` from PR #811
  readonly writes: WritesEvidence;
  readonly waitsCut?: readonly string[];
  readonly reused?: true;                     // from a #787 checkpoint
  readonly retries?: readonly { readonly reason: string }[];
}

export interface AdvisoryJudgment {
  readonly advisory: true;
  readonly task: string;                      // e.g. "done.grounded", "write.destructive"
  readonly step?: number;
  readonly probability: number;               // 0..1
  readonly threshold?: number;
}
```

How secrets stay out, and how that is enforced rather than hoped:

- There is no field for a parameter value, an extracted value, page text, a URL with a query, or
  a request body. `WriteShape.path` is what `journey-run-record.ts` already writes in 0.29.0 (route
  literals only, parameters masked). `paramsDigest` is an HMAC keyed with
  `~/.jevitate/verify-checkpoint.key` (the key #787 already keeps, mode 0600), so a digest cannot
  be reversed by guessing values, and a secret parameter contributes only its name.
- The zod schema uses `.strict()` on every object and bounds every string (`reason` ≤ 500
  characters, enum fields exact), so a gatherer cannot add a free field by accident.
- A served test writes evidence from a run whose parameters, fixture outputs and page text hold
  marker values, and asserts no marker appears anywhere in the JSON. The same scan runs over every
  recorded fixture in `packages/adjudicator/fixtures/`.

### 2.2 Alternatives rejected

- **Extend `JourneyVerifyReport` and `JourneyRunRecord` in place.** They are output formats shaped
  by their renderers; `openAtClose` is not distinguishable from "not gathered" in either, which is
  exactly the H1/H2 class of bug. A new record with `Known<T>` is the fix, and the old reports are
  derived from it (§6).
- **One schema per subject (run, goal, proof).** Three schemas means three adjudicators. The
  optional sections `doneCheck`, `mutation` and `boundary` keep one schema and one function.
- **Record raw request and response bodies "for replayability".** Refused: secrets must never
  persist at rest, and the adjudicator needs shapes and statuses, not bodies.

### 2.3 What changes from 0.29.0 and how Journeys migrate

- `journey run`, `explore --goal` and `journey verify --mutate` each write `evidence.json`
  beside their result (`logs/<date>/…`, pruned on the same retention). The run record from #790
  stays as it is in 0.30.0 and is marked deprecated in favour of the evidence record.
- Journey files do not change for this contract. Nothing migrates.

## 3. Contract 2: the job done check (#800)

### 3.1 Decision

A **done check** is a path-independent statement about the application's state that is false
before a job is done and true after. It lives on the job in `.jevitate/jobs.json`; a Journey with
no linked job may carry one itself in `metadata.done`. Any Journey that satisfies the job's check
is one witness that the job can be done, so several paths fit without changing the check.

```ts
/** `.jevitate/jobs.json` → jobs[].done, or a Journey's metadata.done when it has no job. */
export interface DoneCheckSpec {
  readonly version: 1;
  /** Where to read: a path on the target origin, opened in a fresh session. `${param}` placeholders allowed; `${secret}` refused at lint. */
  readonly at: string;
  /** The reading. Only kinds that name state, never a step: the `--success` syntax of `textIncludes`, `count`, `attr`, `valueEquals`, `http` (a GET against the origin). */
  readonly check: string;
  /** Default `fresh`: open a new browser context with the run's auth and read. `in-run` is allowed only as an extra reading, never as the deciding one. */
  readonly session?: "fresh";
  /** Optional: what makes the "before" reading false for a Journey that creates its own data, e.g. the parameter whose value must not already be present. */
  readonly distinguishedBy?: readonly string[];
}

export interface DoneCheckEvidence {
  readonly spec: DoneCheckSpec;               // placeholders, never resolved values
  readonly before: DoneReading;               // fresh session, before step 1
  readonly after: DoneReading;                // fresh session, after the last step and the end state
  readonly inRun?: DoneReading;               // optional extra reading on the run's own page
}

export interface DoneReading {
  readonly value: Known<boolean>;
  readonly session: "fresh" | "run";
  readonly at: "pre" | "post" | number;       // step index for in-run
  readonly durationMs: number;
}
```

The verdict rule (§4) is small enough to state here:

| `before` | `after` | `job.attainment` | `basis` |
|---|---|---|---|
| false | true | `achieved` | `done-check` |
| false | false | `not-achieved` | `done-check` |
| true | any | `unverified` | `already-true` |
| unknown | any, or any | unknown | `unverified` | `reading-unknown` |
| no `doneCheck` section | | `unverified` | `no-check` |

"Already true" is reported, not failed: it proves nothing either way (the same stance as #202's
vacuous checks). The way out is a Journey that makes its own data, so `before` is false: the TRIZ
state pass calls this S2, "own data per replay", and `distinguishedBy` names the parameter that
does it so lint can warn when a check cannot be false before the run.

**No check.** Attainment is `unverified`, with `basis: "no-check"`. Lint warns `missing-done-check`
on a promoted Journey whose job has none, and the review sheet shows it. The exit code does not
change in 0.30.0 (§6.3, decision 2 for the owner).

**Fresh session.** The `after` reading opens a new browser context with the same auth (storage
state or persona) and navigates to `at`. A page that says "Saved" with nothing stored reads false
here. This also absorbs the "state across replays" problem: nothing is compared across replays, so
nothing needs to be the same across them.

**How a Journey and a job relate.** `metadata.job` already links a Journey to a job (#433). The
done check belongs to the job, because it is a statement about the job's outcome and not about one
path. `journey run <id>` evaluates the linked job's check by default; `--no-done-check` skips it
and reads `unverified`; `explore --goal --job <id>` uses the job's check as the run's success
check, which is what lets exploration say "this path failed, but the job can be done" or "no way
found within budget" (never "impossible"; the lab's no-route precision was 56%).

**Reconcile (#795).** Before a retry or a resume of an automation run, the done check is read
first. If it is already true, the retry does not run and the result says why. That is the whole
reconcile step for 0.30.0: one contract instead of a new prepare/commit/reconcile protocol. Each
write's receipt is its `WriteShape` entry in the evidence (`status`, `refused`), which is value-free
and already recorded.

### 3.2 Alternatives rejected

- **A done check per Journey only.** Several paths to one job would carry copies of one check,
  and exploration could not score "reached the goal by any route" (#807 names this as the reason).
- **Judgment plus a generated postcondition.** Measured: +37 points false rejects, 0 reduction in
  false passes (`x-postcondition`).
- **A second replay as the "before".** The before reading is a read in a fresh session, which
  takes seconds, not a replay.
- **In-run reading as the deciding one.** It is the reading a page can fake ("Saved" with nothing
  stored), and #647's read-back rule already exists because of that.

### 3.3 What changes from 0.29.0 and migration

- `jobs.json` gains an optional `done` field; existing jobs are valid without it and read
  `unverified`. An approved job whose `done` is added becomes stale and needs re-approval, as any
  job change does today.
- `journey run` output gains `job: { attainment, basis }`; `explore --goal` gains the same, and a
  pass accepted by `grounded-judgment` alone reads `unverified`.
- Existing `endState` checks stay what they are: a Journey's own claims about its path. A done
  check does not replace them; it is read in a different session and belongs to the job.

## 4. Contract 3: the adjudicator (#812)

### 4.1 Decision

A new private package, `packages/adjudicator` (`@jevitate/adjudicator`), bundled into the CLI like
every other private package. It holds the evidence schema (§2), the verdict types, and one pure
function. It depends on `zod` and nothing else: not `@jevitate/domain` (which holds the clock), not
`node:*`, not Playwright, not any model gateway.

```ts
export interface Verdict {
  readonly rules: RulesVersion;               // "v1"
  readonly job: JobVerdict;
  readonly checks?: ChecksVerdict;            // only when evidence.mutation is present
  readonly boundary?: BoundaryVerdict;        // §6.2
  readonly reasons: readonly string[];        // code-templated
}

export interface JobVerdict {
  readonly attainment: "achieved" | "not-achieved" | "unverified";
  readonly basis: "done-check" | "already-true" | "reading-unknown" | "no-check" | "harness";
}

export interface ChecksVerdict {
  readonly verdict: "sensitive" | "insensitive" | "inconclusive";
  readonly assertions: readonly { readonly site: string; readonly verdict: AssertionVerdict; readonly provedBy?: string; readonly relaxedSites?: readonly string[] }[];
  readonly reason?: string;
  /** From target trust (§5.2): a proof on a target that cannot be reset is reported, never counted by a strict gate. */
  readonly countsForGate: boolean;
}

export function adjudicate(evidence: RunEvidence, rules?: RulesVersion): Verdict;

/** Re-judge a stored record under another rule set and say which verdicts would move. */
export function rejudge(evidence: RunEvidence, from: RulesVersion, to: RulesVersion): {
  readonly before: Verdict; readonly after: Verdict;
  readonly moved: readonly { readonly field: "job.attainment" | "checks.verdict" | `assertion:${string}`; readonly from: string; readonly to: string }[];
};
```

What moves into the package from 0.29.0, with no verdict changing: `classifyMutation`,
`classifyMutationPlain`, `provenSensitive`, `judgeAssertions` and `mutationProofVerdict` from
`packages/journey/src/mutation-proof.ts`, in the form PR #811 leaves them (its `required` and
`evaluated` fields are part of the v1 rules). `mutation-proof.ts` keeps planning and replay
description (`planJourneyMutations`, `mutationReplay`, the targeted search), which are about what
to run, not about what it means.

What stays outside, by design: anything that opens a browser, reads a clock, reads a file or calls
a model. `journey-verify.ts` becomes a gatherer: it runs replays, fills `MutationEvidence`, calls
`adjudicate`, and renders. `journey-run` and the goal loop do the same for `doneCheck` and
`boundary`.

**The purity check** is three tests in the package:

1. `package.json` dependencies are exactly `{ zod }`; `src/**` imports nothing from `node:`,
   `playwright`, `@jevitate/*` or any model package (a unit test reads the files; the existing
   `scripts/check-clock.mjs` already rejects `Date.now()` and timers repo-wide).
2. `adjudicate(e)` deep-equals `adjudicate(structuredClone(e))` for every recorded fixture, and
   deep-equals itself when `e.judgments` is emptied. The second assertion is "Jev advises, code
   adjudicates" made structural: removing every advisory judgment never moves a verdict.
3. A fuzz over `Known<T>` fields: flipping any `known: true` fact to `known: false` can move a
   verdict only towards `unverified` or `inconclusive`, never towards `achieved` or `sensitive`.

**The four values on #812**, and where each is met:

- Fast, browserless tests: `packages/adjudicator/src/*.test.ts` run under the `unit` project; the
  combinations are tables, not replays. The soundness suite's 4.5 minutes stay for gathering only.
- A replayable record: `rejudge` over `packages/adjudicator/fixtures/*.json`, recorded once from
  the served soundness rows (`journey-verify-soundness-served.test.ts`) through an
  `JEVITATE_RECORD_EVIDENCE=<dir>` switch on that suite.
- Typed honesty about unknowns: `Known<T>` everywhere a gatherer can fail, and test 3 above.
- "Jev advises, code adjudicates" visible in the layout: the package has no model dependency and
  test 2 proves the judgments are inert.

### 4.2 Alternatives rejected

- **Put the function in `@jevitate/domain`.** Domain holds the clock and is imported everywhere;
  the import boundary would be unenforceable by a package-level check.
- **Keep the rules in `mutation-proof.ts` and only add fixtures.** That gives the fast tests but
  not the replayable record, and leaves `journey-verify.ts` deciding verdicts in the same file
  that gathers them, which is where the 0.29.0 false provens came from.
- **A CLI command or MCP tool `adjudicate`.** Nothing outside needs one yet; adding an MCP tool
  changes `ALLOWED_TOOLS`. `rejudge` is reachable through `journey review --rejudge <rules>` only
  if a later release wants it.

### 4.3 What changes from 0.29.0

The `--json` report of `journey verify --mutate` is rendered from the verdict and keeps every field
it has today (`mutations[]`, `assertions[]`, `summary`), with the vocabulary change in §6.
Acceptance for the move: re-judging the recorded soundness rows gives the same verdict for every
row, assertion by assertion, and the served suite's expectations do not change.

## 5. Contract 4: run modes and trust (#792, #793, #794, #798, #799)

### 5.1 Decision

Two run modes, one engine, one Journey format. **The mode is a function of human-written target
configuration and nothing else.** No argument on any command or MCP tool names the mode, and a
target the configuration does not know runs in automation mode.

```ts
export type RunMode = "test" | "automation";

/** environments.json (committed, PR-reviewed) → environments[name].trust, and targets.json (operator's home file) → [origin].trust. */
export type TargetTrust =
  | "test"        // a declared test environment that can be reset; drafts may run; never waits for a person
  | "harness"     // #802: a UI harness over a mock backend; feasibility only, never a job verdict
  | "production"  // production: true; refusals as today, mcpRun lifts them per origin
  | "unknown";    // nothing declared this origin

export function runModeFor(trust: TargetTrust): RunMode {
  return trust === "test" || trust === "harness" ? "test" : "automation";
}
```

`trust` is a new key in `.jevitate/environments.json` and in `~/.jevitate/targets.json`. When both
name an origin, the stricter wins (`production` > `unknown` > `harness` > `test`), so a repo file
cannot declare test mode for an origin the operator's file calls production. `production: true`
stays honoured as `trust: "production"`. `synthetic: true` does not imply `test`: it is a statement
about data, not about who may be waited for.

What each mode guarantees:

| | Test mode | Automation mode |
|---|---|---|
| Target | `trust: test` or `harness` | everything else, including a `baseUrl` nobody declared |
| A human step (handback, approval, secret) | never waits: fails `E_HUMAN_STEP_IN_TEST_MODE`, or uses the target's `secretFields` test credentials | holds the run durably (#793, #798) until a person answers at a terminal |
| Destructive control, off-allowlist write | allowed within the declared environment; the record shows it | refused unless `mcpRun` lifts it, as 0.29.0 |
| Which Journeys run | promoted, or a draft with `--allow-draft` | promoted with an approval a person made (`tty` or `pr-review`) |
| Mutation proof | runs; `countsForGate: true` | runs; reported with `countsForGate: false` and the sentence "a proof's strength depends on a target you can reset" |
| Job attainment | from the done check | from the done check; `harness` forces `unverified` with `basis: "harness"` |
| Jev write sentinel (#794) | logging only | shadow mode in 0.30.0: records what it would have held, gates nothing |

### 5.2 The trust table

Who may do what. "Loosen" means widening what a run may do; "tighten" means narrowing it.

| Actor | Set a target's `trust` | Promote a Journey for test-mode runs | Promote for automation-mode runs | Loosen site policy or promote a mission target | Approve a held action | Supply a secret value |
|---|---|---|---|---|---|---|
| A person at a terminal (`tty`) | yes, by editing the file | yes | yes | yes | yes (`jevitate inbox approve`, typed at a TTY) | yes: `--secret-field`, `targets.json`, visible handback |
| A verified PR review (`pr-review`) | yes, through git | yes | yes | n/a | no | no |
| CI (`ci`) or a scripted escape hatch (`non-interactive`) | no | yes | **no** | no | no | `secretFields` from the runner's environment, test targets only |
| An agent over MCP (`mcp`) | **no** (no tool writes either file) | yes (`promote_journey`, recorded as `mcp`) | **no** | **tighten only** (§5.4) | **no** (`approve_action` refuses, as today) | **no** (`E_SECRET_PARAM_OVER_MCP`, as today) |
| An agent with file access | can forge any of the above | | | | | |

The last row is the honest one. #799 asks for provenance an agent cannot forge; this design does
not provide it and says so (§5.5).

### 5.3 How secrets come back to MCP in automation mode (#798, #809)

In 0.29.0 a Journey that needs a secret cannot run or be proved over MCP at all, and `targets.json`
is not read over MCP because "an agent can promote a Journey over MCP, so it could choose where
the value goes" (`docs/journeys.md`). The mode contract closes that attack differently: an
automation-mode run needs an approval a person made, so an agent's own promotion cannot start one.
With that in place:

- In automation mode over MCP, `run_journey` on a Journey with a secret parameter does not refuse.
  The run proceeds to the secret step and then **holds** (§5.4). It resumes in one of two ways,
  both chosen by a person: `vault-autofill`, when the operator's `targets.json` declares a
  `secretFields` binding for that origin (code types it, origin-bound, as in 0.29.0 on the CLI);
  or `visible-handback`, when the person runs `jevitate inbox resume <id>` at a terminal, which
  opens the held session headed for them to complete the step. The agent sees `outcome:
  "held"` and later the resumed result, never the value.
- In test mode over MCP, the same Journey runs with the test target's `secretFields` or fails
  `E_HUMAN_STEP_IN_TEST_MODE` before any browser opens. A value passed as a parameter is still
  refused by name, in both modes: `E_SECRET_PARAM_OVER_MCP` does not change.
- Of #809's remaining limits, this resolves "a login Journey can't be proved over MCP" for
  `run_journey`, `verify_journey`, `journey_readiness` and `chain_journeys` on an automation-mode
  target (they hold at the secret step). It does not resolve the CLI argv forms (`regression`,
  `verify-fix`, `journey migrate --labels` still warn or do not), nor a literal secret in a
  `run_check` params file; those stay documented limits, and the CLI argv warning is extended to
  the forms that lack it as a small Junior deliverable.

### 5.4 Holds, approvals and the ratchet (#793, #799)

**A hold** is a durable record plus a checkpoint. It reuses the #787 checkpoint layout
(`.jevitate/logs/verify-progress/` becomes `.jevitate/logs/holds/`), written atomically with the
same key. The record binds what the person is approving:

```ts
export interface HoldRecord {
  readonly version: 1;
  readonly kind: "approval" | "handback" | "secret";
  readonly journey: { readonly id: string; readonly hash: string };
  readonly paramsDigest: string;              // keyed, as in RunEvidence
  readonly target: { readonly origin: string; readonly trust: TargetTrust };
  readonly pending: { readonly step: number; readonly control?: string; readonly write?: { readonly method: string; readonly path: string } };
  readonly checkpoint: string;                // path of the resumable run state, value-free
  readonly createdAt: string; readonly expiresAt: string;
  readonly answer?: { readonly decision: "approved" | "rejected"; readonly provenance: ApprovalProvenance; readonly at: string };
}
```

`queue_action` over MCP creates the hold and returns its id; the run stops. `approve_action`
over MCP keeps refusing. `jevitate inbox approve <id>` at a TTY writes `answer`, and
`jevitate inbox resume <id>` (or the queue runner, #797) continues from the checkpoint only if the
Journey hash, parameter digest, target and pending action in the record still match: a changed
Journey needs a new approval. An expired hold ends the run `inconclusive` with `E_HOLD_EXPIRED`.
Nothing in the record is a value.

**The ratchet (#799).** Over MCP, `site_policy` may only produce a policy that is at least as
strict as the effective one on every axis (pacing, interval, budget, quiet hours); a looser one is
refused with `E_POLICY_LOOSEN_OVER_MCP`. `mission_targets` can no longer promote a target over MCP
(`E_TARGET_PROMOTE_OVER_MCP`); promotion is a CLI act, as `docs/safety.md` already calls it. An
authored `allowedOrigins` (the other loosening path `safety.md` lists) joins the run's write
allowlist only in test mode; in automation mode it needs `mcpRun.allowOffAllowlistWrites`.
`promote_journey` over MCP stays, and its `mcp` channel authorises test-mode runs only, which
answers the question #799 leaves open.

**The sentinel (#794).** In automation mode, before each write, Jev reads the structured pending
action (control name, method and path shape, a page summary) and the job story and returns
`destructive` and `outside-intent` probabilities. In 0.30.0 it runs in shadow mode: the
judgment is appended to `evidence.judgments` with `advisory: true`, a "would have held" counter
is reported, and nothing is held. The measurement deliverable reports precision and recall on a
seeded set of destructive and harmless writes; gating is a 0.31.0 decision made on those numbers.
Even then it can only add a hold, never remove a refusal, which the adjudicator's purity test 2
already guarantees: judgments are inert for verdicts, and the code floor stands on its own.

### 5.5 What this does and does not resolve about forged provenance

Resolved: an agent that has only the MCP surface cannot change a target's trust, cannot start an
automation-mode run on its own promotion, cannot loosen a policy, cannot promote a target, and
cannot read or move a secret value. Tests: for each MCP tool that starts a run, a served test with
a target declared `production`, one declared `unknown` and one undeclared `baseUrl` shows the run
is in automation mode whatever the arguments say, and that `promote_journey` followed by
`run_journey` on such a target refuses `E_APPROVAL_CHANNEL_FOR_MODE`.

Not resolved: an agent with write access to `.jevitate/` or `~/.jevitate/` can write any file this
design trusts, including `trust: "test"` and `provenance.channel: "tty"`. The control for that is
the one `safety.md` already states, git review of `.jevitate/` with `check --require-approvals`,
extended to a `--require-trust` check that fails CI when an environment's `trust` changed outside a
reviewed PR. Cryptographic provenance (signing approvals with a key the agent cannot read) is a
possible 0.31.0 item; it is not in 0.30.0 because the key would have to live somewhere the same
agent cannot reach, and nothing in the current layout gives that.

### 5.6 Alternatives rejected

- **Mode as a flag (`--mode test`).** The caller decides, so an agent decides. Refused by #792.
- **Mode from the Journey file.** A Journey is a path; the same path runs on staging and on
  production. The target is what differs.
- **Automation mode refuses secrets outright, as 0.29.0 does.** It keeps the limit that a login
  Journey cannot be automated over MCP, which contradicts "an automation platform".
- **Read `targets.json` over MCP without the approval-channel rule.** This is the attack
  `journeys.md` names, and it stays closed.

### 5.7 What changes from 0.29.0 and migration

- Every target not declared `trust: "test"` is automation mode. For a user whose targets are
  undeclared that means: drafts no longer run over MCP (they did not before either, so no change),
  a Journey approved over MCP no longer runs over MCP (change; the fix is one typed `journey
  promote`, as 0.29.0 already required for approvals from before 0.29), and a Journey with a
  secret parameter holds instead of refusing (change, an improvement).
- CLI runs: unchanged in what they may do; they now report `run.mode` in the evidence and warn
  on stderr when a draft runs on an automation-mode target.
- `environments.json` and `targets.json` accept `trust`. Existing files are valid; `production:
  true` maps to `trust: "production"`.

## 6. Contract 5: result vocabulary and exit codes (#807, migration from `proven`)

### 6.1 The vocabulary

| 0.29.0 | 0.30.0 | Where |
|---|---|---|
| `verdict: "proven"` | `verdict: "sensitive"` | `journey verify --mutate --json`, readiness, review |
| `verdict: "insensitive"` | unchanged | |
| `verdict: "inconclusive"` | unchanged | |
| (none) | `checks.countsForGate: boolean` | from target trust |
| (none) | `job: { attainment, basis }` | `journey run`, `explore --goal`, `run_journey`, `get_mission_result` |
| `verifiedBy: "grounded-judgment"` → `succeeded` | `succeeded` with `job.attainment: "unverified"` | goal runs |
| `mutationProofPolicy: "require-proven"` | `"require-sensitive"`; `require-proven` accepted as an alias with a deprecation warning until 0.32.0 | `project.json` |
| `goalOutcome: "blocked"` on a wall, session loss, off-allowlist or new tab | `goalOutcome: "boundary"` with `boundary.kind` | goal runs |

`sensitive` is chosen over `noticed` or `caught` because it is already the per-assertion word in
the public JSON (`sensitive`, `insensitive`, `cascade`), so a reader learns one word fewer, and
because it says what was shown: the checks are sensitive to the mutations that were run, under the
conditions they ran in.

**Deprecation path for `proven`**, since `--json` is a public contract: for 0.30.0 and 0.31.0 the
report carries both `verdict` (new word) and `verdictLegacy` (`"proven"` when `verdict` is
`"sensitive"`, otherwise equal to `verdict`), the human line prints the new word, and the
changelog names the removal release (0.32.0). A reader keyed on `verdict === "proven"` breaks in
0.30.0 unless it reads `verdictLegacy`; the release notes say so in the first paragraph.

### 6.2 Boundary outcomes (#807)

```ts
export interface BoundaryEvidence {
  readonly kind: "wall" | "session" | "off-allowlist" | "new-tab";
  readonly step: number;
  readonly origin?: string;                   // the origin an off-allowlist or new-tab stop names
  readonly signal: "http-401" | "http-403" | "paid-control" | "login-url" | "write-refused" | "tab-opened";
}
```

These are the four boundaries the lab proved (10/10 each, no false boundary on clean cells). The
opaque boundary is not shipped: it fires on any canvas or iframe and was not tested beside a
working route. The no-route reason is not shipped: precision 56%. A run that hits a boundary
reports `goalOutcome: "boundary"`, `goalReason` naming the signal, and the origin where there is
one, instead of today's `blocked / gave-up` with raw control JSON in the reason.

### 6.3 Exit codes: the decision for the owner

Exit codes are a public contract. Three changes are on the table; the recommendation is the first
two now and the third behind a setting.

| # | Change | Today | Proposed | Recommendation |
|---|---|---|---|---|
| 1 | A boundary run (wall, session, off-allowlist, new tab) | exit 1 `defects-found` | exit 2 `inconclusive`, `missionOutcome: "inconclusive"`, `goalOutcome: "boundary"` | **Make the change.** Every one of the 39 no-route and wall baseline runs read as a defect of the app, and none was. Exit 2 already means "the run could not do its work and proves nothing", which is the truth of a wall. No new code is added, so CI scripts that branch on 0/1/2 keep working; a script that treated 1 as "the job is broken" was being misled. `sso-only` moves with the rest (it was already exit 2 by accident). |
| 2 | A Journey run whose steps pass but whose done check reads false | exit 0 `ok` | exit 1 `defects-found`, `failure.kind: "done-check-failed"` | **Make the change.** This is the false pass the product exists to catch; a Journey that passes its own claims while the job did not happen is a defect, of the app or of the Journey, and either way not `ok`. It only applies when a done check exists, so no existing Journey changes behaviour until its job declares one. |
| 3 | A pass with no done check (`job.attainment: "unverified"`), including a judgment-only goal pass | exit 0 | exit 2 | **Not by default in 0.30.0.** Ship it as `doneCheckPolicy: "require"` in `project.json` and a `--require-done-check` flag, default `advisory`, and announce `require` as the 0.31.0 default. Reason: the 8 of 20 rate is on a seeded fixture with one model, rates on real apps are unknown (`implementation-plan.md`, "Not established"), and flipping every `explore --goal` without `--success` to exit 2 at once would break CI for users who use goal runs to explore rather than to gate. |

No exit code number changes meaning. `MISSION_EXIT_CODES` in `packages/domain/src/mission-outcome.ts`
gains no entry; `GOAL_OUTCOME_FOLD` gains `boundary → inconclusive`; `journeyExitCode` gains the
done-check case.

### 6.4 Migration of existing Journeys

- No Journey file changes for the vocabulary.
- A Journey whose job gains a `done` check may start exiting 1 where it exited 0. That is the
  intended discovery; the review sheet shows the before/after readings so the author can see
  whether the check or the Journey is wrong.
- `require-proven` in `project.json` keeps working with a warning.

## 7. The experiment gate (#800) and what changes if it goes the other way

The plan has a gate before the vocabulary, policy defaults and docs land: #800's three-arm
comparison on the accuracy lab's seeded defects (`test/fixtures/accuracy-lab`: `j1-5xx`,
`j2-stall`, `j3-effort`, `j3-deadend`, `clean`) plus deliberately weak Journeys (a check that
passes without the write; a check on a page that says "Saved" while the 500 is masked; a Journey
that reads an existing record).

| Arm | What it runs | What counts as "caught" |
|---|---|---|
| Lint only | `journey lint` | a `no-persistence-check` or equivalent warning on the weak Journey |
| Witness + Jev | `journey run` with the job's done check, Jev advisory on the story | `job.attainment: "not-achieved"` or `unverified` on the defective cell |
| Mutation proof | `journey verify --mutate` on a reset target | `insensitive` or `inconclusive` on the defective cell |

Prediction, as the issue states it: the witness arm catches at least as many as mutation proof,
with no more false alarms, in at most 10% of the time. Three outcomes and what each changes:

- **Holds.** Mutation proof becomes opt-in strength evidence: `mutationProofPolicy` default stays
  `advisory`, `require-sensitive` is documented as a choice for resettable targets, and the
  readiness sheet leads with the job verdict. This is the design as written.
- **Witness catches fewer.** The adjudicator and evidence contracts ship unchanged (they do not
  depend on this result). The done check stays and is reported, but `require-sensitive` remains
  the strict gate's backing on resettable targets, the docs say the witness is necessary and not
  sufficient, and the missed cases are added to the adjudicator fixtures so the rule that would
  catch them can be tried browserless.
- **More false alarms.** The `already-true` and `reading-unknown` rules are the first suspects
  (a check that cannot be false before the run reads `unverified`, which this arm would count as
  an alarm). `distinguishedBy` becomes required for a check on a job that creates data, and the
  experiment is re-run before the vocabulary deliverables continue.
- **Time over 10%.** Ship anyway; the cost is stated in the release notes with the measured
  ratio, as 0.29.0 did for proofs.

The experiment is a frontier deliverable because its arms touch the secret and MCP boundary
(the fresh-session read-back uses the run's auth) and because the result decides a public
default. #801's own test-first (removal alone, annealing, Jev-guided) and #802's
(mock harness against the real stack on `jz-triager-files-issue`) run as experiments in the same
wave; neither ships code beyond its harness in 0.30.0 unless its prediction holds, and the plan
says so per deliverable.

## 11. What is cut, and why

- **Per-write read-back receipts (#795 beyond the evidence shapes).** The done check answers "did
  it land" for the job; a per-write protocol would need a read for every write, which needs a
  per-write check nobody has written. One contract instead of two.
- **Opaque-surface and no-route boundaries.** Refuted or untested on the lab; the plan says
  "report what was searched, never claim a route is absent".
- **Sentinel gating (#794).** Shadow mode only until precision and recall are measured.
- **A new MCP tool for adjudication or re-judging.** Nothing outside needs one; `ALLOWED_TOOLS`
  changes only for `queue_journey` (#797), which the mcp-facade deliverable owns.
- **Path search in the product (#801).** The experiment runs; the code ships in 0.31.0 if the
  prediction holds.
- **A separate "job verdict" command.** The verdict rides on `journey run`, `explore --goal`,
  `run_journey` and `get_mission_result`.
- **Cryptographic provenance.** Named as 0.31.0 (§5.5).

## 12. What I could not establish, and how to test it

1. **That a done check can be made false-before on real apps often enough to matter.** Singletons
   (account settings) are always "already true" in some sense. Test: on Journeeze's five Journeys
   and the accuracy lab's three jobs, write a done check per job and count how many need
   `distinguishedBy`; if more than half do, the lint rule becomes a refusal at promotion.
2. **The witness arm's time ratio.** The before and after readings each open a fresh context;
   on a slow sign-in that could be 10–20 s each. The experiment measures it.
3. **That re-judging recorded soundness rows gives identical verdicts after #811.** The fixtures
   are recorded after the merge, so the comparison is against #811's served expectations, not
   0.29.0's. If a row moves, the rule that moved it is the finding.
4. **The real-app rate of boundary false positives.** Lab: 0 on clean cells across 10 replicates.
   The release-candidate rerun of the whole lab plus the accuracy lab's goal cells through
   `--guards` is the test; a boundary on any accuracy-lab cell blocks the release.
5. **Whether `trust` in two files (repo and home) confuses users.** Test with the docs reviewer
   and one dogfood target; if it does, drop the repo-side key and keep only `targets.json`.
6. **The sentinel's precision and recall.** Measured before any gating.
7. **PR #811's conflict count against the 0.30.0 line.** This machine's git (2.34) cannot run
   `merge-tree --write-tree`; the 21 is the owner's figure from the PR worktree.
